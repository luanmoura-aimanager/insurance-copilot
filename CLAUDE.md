# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-agent system that turns Brazilian home-insurance *condições gerais* (general terms registered with SUSEP) into a queryable knowledge base. It answers **coverage-structure** questions ("which insurers cover windstorm without a deductible?"), not pricing — the corpus describes products, and prices live in individual customer policies which are out of scope.

The project is mid-build. What exists: the data pipeline (harvester + validated extraction schema + `app/extraction/` LLM pipeline), a FastAPI/Postgres skeleton, the ORM models + Alembic migrations (`app/models.py`), per-call cost attribution (`app/cost.py` + `pricing.json`) wired into the agent graph, a standalone Postgres MCP SQL server (`mcp_servers/`), the agent graph (`app/agents/graph.py`: LLM supervisor de três rotas + single-pass SQL worker + RAG worker + synthesizer — see below) served at `POST /ask` (protected by Bearer auth + rate limiting — `app/auth.py`, `app/limits.py`), a testcontainers-backed test suite, the RAG worker's **vector infrastructure** (pgvector + `clause_chunk` — R1, storage only), a **materialização dos chunks** (`app/rag/chunking.py` + `index.py` — R2a: o texto de cada chunk é montado e gravado, com `embedding` NULL) a **passada de embedding** (`app/rag/embedding.py` + `embed.py` — R2b: Voyage `voyage-4-lite`, `input_type="document"`, commit e `cost_event` por lote) a **busca por similaridade** (`app/rag/search.py::search_clauses` — R3a: função testável, `input_type="query"`, limiar de relevância ainda por calibrar) e a **ligação disso com o grafo** (R3b: supervisor de três rotas + nó `rag_worker`, grafo single-hop — ver abaixo). What does *not* exist yet: a calibração do limiar (o número está decidido, não medido), a ReAct refinement loop in the SQL worker, and the WhatsApp surface. See the Roadmap in `README.md` for current state before assuming a component exists.

## Architecture & key decisions

**Async-only data layer.** `app/db.py` uses SQLAlchemy 2.0 async (`asyncpg` driver). The `DATABASE_URL` **must** use the `postgresql+asyncpg://` scheme, not plain `postgresql://`. The async route (`/health/db`) injects a session via FastAPI `Depends(get_session)`.

**A engine é preguiçosa: `DATABASE_URL` é lida em runtime, não no import.** `app/db.py` não constrói mais nada no nível do módulo. `_sessionmaker()`, cacheado com `@lru_cache(maxsize=1)`, lê o env, normaliza a URL e cria a engine + o `async_sessionmaker` **na primeira chamada**; `SessionLocal()` é uma função que delega pra ele. O motivo: com `os.environ["DATABASE_URL"]` no topo do módulo, qualquer `import app.main` num ambiente sem banco configurado morria com `KeyError` **no import** — inclusive durante a *coleta* do pytest, antes do testcontainers ter subido o Postgres. Esse bug voltou 4×, sempre disfarçado de "ordem de fixture", e é o que impedia um CI sem `.env`. Três detalhes carregam peso. (1) O `lru_cache` **é** a engine única do processo: sem ele, cada `SessionLocal()` criaria uma engine (e um pool) nova e vazaria conexões — não construa engine por chamada, só via o cache. (2) `SessionLocal` continua sendo um **atributo chamável do módulo** de propósito: 6 scripts fazem `from app.db import SessionLocal` e `tests/test_cost_graph.py`/`tests/test_synth.py` trocam esse atributo com `monkeypatch.setattr("app.db.SessionLocal", ...)` — renomear quebra os dois lados. É também por isso que o import de `app.db` dentro de `record_call_cost` continua sendo local: o motivo original (importar `app.db` exigia env) caiu, mas o import tardio é o que resolve `SessionLocal` no momento da chamada e faz o monkeypatch pegar. (3) `load_dotenv()` fica **no topo**: em dev local o `.env` continua sendo a fonte da URL, e em CI, sem arquivo, é no-op — ele não exige nem lê a variável. `tests/test_lazy_db.py` é a trava: roda `import app.main` (e cada degrau da cadeia: `app.db`, `app.cost`, `app.agents.graph`) num **subprocesso** com env limpo, cwd fora do repo e `load_dotenv` neutralizado, porque dentro do processo do pytest o env já está populado pela fixture do container e não se prova nada. Ele também **chama `SessionLocal()` pra valer** e roda um `SELECT 1` no que voltou: nenhum outro teste faz isso (os de custo trocam o atributo por monkeypatch, e a fixture `client` sobrescreve `get_session`), então sem esse assert um bug *dentro* de `SessionLocal` passaria pela suíte inteira verde — verificado plantando o bug.

**As gambiarras de ordem de fixture da F3/F4 agora são redundantes.** `ask_client` em `tests/test_cost_graph.py` e `tests/test_synth.py` pede `db_url`/`cost_rows` antes só pra garantir que o container (e portanto `DATABASE_URL`) existisse antes de `import app.main` — com a engine preguiçosa isso não é mais necessário, e os docstrings dessas fixtures descrevem um problema que não existe mais. **Foram mantidas de propósito** na fatia da correção (remover é ruído separado, e `cost_rows` continua obrigatória nos testes que de fato contam linhas em `cost_event`); quem mexer nesses arquivos depois pode simplificar a assinatura sem medo.

**CI (`.github/workflows/ci.yml`).** `pull_request` + push na `main`; ubuntu-latest, Python 3.11, `pip install -r requirements.txt`, `pytest -q`. O job **não** seta `DATABASE_URL` nem cria `.env`, e isso é o ponto: quem sobe o Postgres é o testcontainers dentro da própria suíte (o runner já traz Docker; `TESTCONTAINERS_RYUK_DISABLED` vem do `conftest.py`). Ou seja, o CI só é verde por causa da engine preguiçosa — ele é a prova viva da correção, não só um gate. Também não precisa de secrets: nenhum teste gasta dinheiro (todos usam fakes), então `ANTHROPIC_API_KEY` não entra.

**Port 5433.** docker-compose maps Postgres to host `5433` (not the default 5432) to avoid colliding with a local Postgres; `.env.example` reflects this.

**The corpus is general terms, not policies.** This is the central scoping decision and it shapes the schema: a document describes a *product*. The extraction grain is therefore **(insurer × coverage)**, and coverages are normalized **by peril, not by commercial name**, because insurers bundle perils differently. That makes `coverage ↔ peril` many-to-many. The tables are built in `app/models.py`: `policy_document`, `coverage` (includes a nullable `plan` free-text commercial tier), `peril`, `coverage_peril` (join), `exclusion` (scope = general or per-coverage). Categorical columns feed the future SQL worker; raw-text columns feed the future RAG worker.

**Infra de vetores (R1 do worker RAG): `clause_chunk` + pgvector.** Esta fatia foi **só armazenamento** — quem passou a gravar linhas é a R2a (`app/rag/`, abaixo); embedding e retrieval continuam pendentes (R2b/R3) e não existe nó novo no grafo. A imagem do Postgres virou `pgvector/pgvector:pg16` **nos dois lugares** (`docker-compose.yml` e o `PostgresContainer` do `tests/conftest.py`): é a mesma `postgres:16` com a extensão compilada, e se as duas divergirem o `CREATE EXTENSION vector` da migration quebra justamente onde ninguém olha (CI). A tabela é **separada de propósito**: o texto já existe em `exclusion.clause_text` e `coverage.deductible_rule_text`, mas lá o grão é a *linha extraída* e aqui é o **chunk** — uma cláusula longa vira vários pedaços, cada um com o seu vetor; guardar o embedding na tabela de origem forçaria um chunk por linha e amarraria o schema de domínio ao modelo de embedding da vez. A origem do chunk é um **arco exclusivo** — `exclusion_id` **ou** `coverage_id`, exatamente um, imposto pelo check `ck_clause_chunk_exactly_one_source` — e os uniques `(exclusion_id, chunk_index)` / `(coverage_id, chunk_index)` são o que torna a re-indexação idempotente. O modelo é **voyage-4-lite / `EMBEDDING_DIM = 1024`** (multilíngue, e o corpus é pt-BR; barato; dimensão menor deixa o índice HNSW leve); a dimensão fica **no tipo da coluna** porque o Postgres precisa dela pra indexar, então trocar de modelo é migration, não config. `embedding` e `embedding_model` são nullable porque chunking e embedding são passos separados: a linha nasce com o texto e recebe o vetor depois — `NULL` = "ainda não indexado".

**A migration do `clause_chunk` (`d3f8a1c60b47`) é escrita à mão, e o índice mora nos dois lados.** O autogenerate enxerga a tabela e a coluna `vector(1024)`, mas não emite nem o `CREATE EXTENSION` (sem ele o `CREATE TABLE` falha com *"type vector does not exist"*) nem o índice HNSW (Alembic não modela operator class), então a ordem extensão → tabela → índice é escrita na mão. O `downgrade()` desfaz índice → tabela e **não dropa a extensão**: ela é do banco, não desta tabela. O índice é criado com SQL cru na migration **mas também declarado no `__table_args__`** do modelo (`Index(..., postgresql_using="hnsw", postgresql_ops={"embedding": "vector_cosine_ops"})`) — sem essa declaração o próximo `alembic revision --autogenerate` vê um índice que o modelo não conhece e emite um `drop_index`, derrubando o índice de vetor de brinde numa migration sobre outro assunto. `alembic check` é o que trava isso (verificado: com o índice só na migration, ele acusa `remove_index`).

**O arco exclusivo (`a4c91e5d7f28`) substituiu o ponteiro polimórfico da R1.** O desenho original era `source` (texto) + `source_id` (id **sem FK**), e tinha dois furos que o code review pegou. (1) `source_id` não era chave estrangeira: apagar a exclusão de origem deixava o chunk apontando pro vazio e — como a re-extração reusa ids — o chunk passava a citar uma cláusula *diferente*, destruindo exatamente a garantia de "citar a origem" que a coluna existia pra dar. (2) O `UniqueConstraint(source, source_id, chunk_index)` **não** impunha idempotência: `source_id` era nullable e o Postgres trata `NULL`s como distintos num índice único, então duas linhas idênticas entravam as duas (verificado empiricamente). Agora são duas FKs de verdade (`exclusion_id`, `coverage_id`) com um check XOR (`(exclusion_id IS NOT NULL) <> (coverage_id IS NOT NULL)`); `coverage_id` **mudou de significado** — era cópia denormalizada da cobertura dona da exclusão (que podia divergir de `exclusion.coverage_id`), agora é o braço "este chunk é a regra de franquia desta cobertura". A migration é escrita à mão e faz `DROP COLUMN`, o que só é seguro porque `clause_chunk` está **vazia em todo ambiente** (a R1 entregou só armazenamento) — não há backfill. Ela também cria `ix_clause_chunk_document_id`: o Postgres não indexa coluna filha de FK sozinho, e sem isso todo `DELETE` em `policy_document` viraria seq scan na maior tabela do schema (`exclusion_id`/`coverage_id` já saem indexadas pelos dois índices de idempotência).

**As FKs do arco são compostas com `document_id`, e é isso que fecha o buraco de verdade.** Com FK simples (`exclusion_id → exclusion.id`) sobrava um terceiro caso ruim, além dos dois de cima: nada obrigava `document_id` a ser o documento da origem, então um chunk com `document_id` do documento B e `exclusion_id` de uma exclusão do documento A entrava sem reclamar (verificado empiricamente — passava). E aí o buraco reabria pela porta lateral: `delete_document_by_hash(A)` apaga chunks **por `document_id`**, não veria esse chunk, e estouraria `ForeignKeyViolation` ao apagar a `exclusion` — o documento pela metade que esta fatia inteira existe pra impedir. As FKs são `(document_id, exclusion_id) → exclusion(document_id, id)` e `(document_id, coverage_id) → coverage(document_id, id)`; o Postgres exige unique/PK no lado referenciado, daí os `UniqueConstraint("document_id", "id")` em `coverage` e `exclusion` — redundantes como unicidade (`id` já é PK), presentes **só** como alvo da FK. O que faz isso conviver com o arco é o **MATCH SIMPLE** (o padrão): se qualquer coluna da FK é `NULL` a constraint não é checada, então o braço não usado fica inerte e só o preenchido é validado. É também o que torna verdadeiro o comentário em `persist.py` de que um `DELETE` por `document_id` cobre os dois braços — antes isso era presunção, agora é garantia do schema.

**Os dois índices de idempotência são únicos parciais, não `UNIQUE` constraints.** Por desenho metade das linhas tem `exclusion_id` `NULL` e a outra metade `coverage_id` `NULL`, então um índice total carregaria uma entrada morta por linha do outro braço — o dobro do tamanho, na tabela que também carrega o HNSW. O predicado (`WHERE exclusion_id IS NOT NULL`) não afrouxa nada: as linhas que ele exclui são exatamente as que o `NULL` já tornava não-conflitantes. Continuam servindo a validação da FK, porque `exclusion_id = $1` implica o predicado. Os nomes seguem `uq_...`, então as mensagens de erro (e os `pytest.raises(match=...)`) não mudaram.

**O `REVOKE`/`GRANT` é guardado por um `DO` block em `pg_roles`.** Role é objeto de **cluster**, não de banco, e a cadeia de migrations só garante objetos do banco: um `pg_dump` restaurado num cluster novo (`pg_dump` não emite roles) chega aqui sem `insurance_ro` e a migration morre com `role "insurance_ro" does not exist` — no Procfile, que roda `alembic upgrade head` no boot, isso é o web process que não sobe. O Postgres não tem `REVOKE ... IF EXISTS` pra role, então o guard é explícito (`_if_role_exists()`). Verificado: dropando a role antes do upgrade, a migration passa.

**O `downgrade()` esvazia `clause_chunk` antes de reconstruir o desenho antigo.** `source` volta como `NOT NULL` e `exclusion_id` some — não há como reconstruir o ponteiro antigo a partir do arco sem inventar dado. Sem o `DELETE`, o downgrade numa base já indexada (o mundo pós-R2) dropava `exclusion_id` e só então estourava em `ADD COLUMN source NOT NULL` com *"column contains null values"*. Descartar chunk é recuperável — texto e embedding saem de re-indexar cláusulas que continuam em `exclusion.clause_text` / `coverage.deductible_rule_text`; morrer no meio do downgrade não é. Enquanto a R2 não existir a tabela está vazia e o `DELETE` é no-op.

**`delete_document_by_hash` apaga `clause_chunk` primeiro.** A ordem é `clause_chunk → coverage_peril → exclusion → coverage → policy_document`: o chunk é o filho mais fundo, referenciando as três tabelas acima dele. Sem isso o DELETE estoura com `ForeignKeyViolation` já em `exclusion` e deixa o documento **pela metade** — o fluxo `--force` de re-extração quebraria assim que a R2 começasse a gravar chunks. `tests/test_delete.py::test_delete_removes_clause_chunks` é a trava, e cobre os **dois** braços do arco (um chunk por exclusão, um por cobertura); foi escrito antes da correção e confirmado vermelho com a FK violation.

**`clause_chunk` fica fora do alcance do worker SQL — em duas camadas independentes.** A tabela está fora do `TABLES` do MCP server (o worker responde por agregação sobre colunas categóricas; expor uma coluna vetorial no `get_schema()` só gastaria contexto), mas isso sozinho não protegia nada: o filtro textual do `run_query` só olha o primeiro token, então um `SELECT * FROM clause_chunk` escrito pelo LLM passaria, e o `LIMIT 100` automático despejaria 100 vetores de 1024 floats (~1 MB de texto) no contexto da chamada seguinte, num projeto que mede custo por chamada.

As duas camadas são: (1) **allowlist de tabela no `run_query`** — `_tabelas_fora_da_allowlist()` extrai os alvos de `FROM`/`JOIN` e rejeita o que não for tabela de domínio nem CTE local; (2) **`REVOKE SELECT ON clause_chunk FROM insurance_ro`** na migration `a4c91e5d7f28`, **cirúrgico** (o `ALTER DEFAULT PRIVILEGES` da `4b285ffad59b` continua valendo pras tabelas futuras, e as tabelas de domínio seguem legíveis). **Nenhuma cobre o caso da outra**, e é por isso que existem as duas: o REVOKE não participa de nada quando `DATABASE_URL_RO` não está configurada e o `_conninfo()` cai silenciosamente pro `DATABASE_URL` admin (o caso do CI, e de qualquer deploy que só setou a URL admin); a allowlist não seguraria uma role com permissão de escrita se o filtro de `SELECT` fosse burlado. A allowlist não é um parser de SQL e não precisa ser — subquery e CTE também usam `FROM`, então toda leitura de tabela passa por lá; `FROM (SELECT ...)` não casa de propósito (o que importa está dentro), e nomes de CTE são coletados à parte pra não virarem falso positivo.

Os testes cobrem os dois lados de cada camada. `test_worker_sql_nao_enxerga_clause_chunk` assere `has_table_privilege` falso pra `clause_chunk` **e verdadeiro pra `exclusion`**, senão um revoke largo demais passaria despercebido derrubando o worker inteiro — mas ele afirma o privilégio da *role*, não que alguém conecte com ela, e é justamente esse limite que a allowlist cobre. `tests/test_sql_allowlist.py` roda **sem banco** (a rejeição acontece antes do `_connect()`) e também tem os dois lados: as tabelas proibidas rejeitadas, e as queries legítimas do domínio — join, alias, subquery, CTE **dentro de subquery** — aprovadas, senão um `return "Error"` incondicional passaria no teste de rejeição e derrubaria o worker em silêncio. **Uma CTE de TOPO (`WITH x AS (...) SELECT ...`) é rejeitada**, e isso é limitação conhecida e agora fixada por teste (`test_cte_de_topo_e_rejeitada_pelo_filtro_de_select`): ela morre no filtro do `SELECT` inicial, não na allowlist. Não é acidente removível — `WITH x AS (...) DELETE FROM ...` é válido no Postgres, então é o `startswith("select")` que impede escrita disfarçada de CTE; liberar `WITH` exige a checagem de escrita olhar o statement final, e é fatia própria. Antes, a CTE de topo estava na lista de "aprovadas" passando pelo motivo errado (a asserção era só "não foi a allowlist") enquanto esta linha anunciava suporte a CTE — a forma que de fato exercita o `_CTE_RE` é a de dentro da subquery, que é a que passa do filtro. O `mcp_servers/test_readonly_role.py` (standalone, não pytest) ganhou uma quarta checagem: `SELECT` em `clause_chunk` esperando `InsufficientPrivilege` — é o único lugar que exercita o REVOKE por uma conexão libpq real autenticada **como** a role, que é o caminho que o worker usa de verdade.

**O que `tests/test_vector.py` prova.** Extensão instalada, round-trip de 1024 floats, ordenação por distância, índice HNSW com a operator class certa, os dois braços ruins do arco, idempotência da re-indexação, o revoke, e dimensão errada rejeitada. Cinco são load-bearing.

Os dois primeiros cobrem a **FK em si**, que é a manchete da correção e mesmo assim não tinha teste nenhum: `test_fk_rejeita_origem_inexistente` (ponteiro órfão) e `test_fk_impede_apagar_a_exclusao_citada` (o dano real do id sem FK não é o `NULL`, é a re-extração reciclar o id e o chunk passar a citar outra cláusula em silêncio). Sem eles a FK inteira podia sumir da migration com a suíte verde — o check XOR continua disparando, os uniques continuam disparando, e o teste de delete passa porque apaga os chunks primeiro de qualquer jeito. `test_fk_composta_rejeita_chunk_de_outro_documento` é o terceiro: prova que `document_id` e a origem do arco têm que concordar, o caso que passava antes da FK composta. O de **distância**: `cosine_distance` vira o operador `<=>`, que num `float[]` comum nem existiria — é ele que prova que o tipo é vetor de verdade; insere os chunks na ordem **inversa** da esperada e consulta nos dois sentidos, porque com a ordem "certa" de inserção o teste passaria mesmo se o `ORDER BY` fosse ignorado. O do **índice**: sem ele, apagar o `CREATE INDEX ... USING hnsw` da migration (ou trocar `vector_cosine_ops` por `vector_l2_ops`) deixaria todo o resto verde — com duas linhas o planner ordena por seq scan de qualquer jeito, e uma opclass errada simplesmente nunca seria usada. O de **dimensão** casa a mensagem `expected 1024 dimensions` em vez de aceitar qualquer `DBAPIError`, que seria satisfeito por uma FK ou um NOT NULL vizinhos sem nunca exercitar a dimensão. Os dois testes de índice checam a **definição** (`(document_id)`, `WHERE (... IS NOT NULL)`), não só a existência da linha em `pg_indexes`: com um `assert indexdef is not None` bastava criar o índice na coluna errada pro teste passar verde com o seq scan intacto — o nome do índice não prova o conteúdo dele. Os testes que esperam falha rodam dentro de `begin_nested()` (savepoint): o INSERT abortado aborta a transação junto, e sem o savepoint derrubaria a transação da fixture que mantém os testes isolados.

**`pgvector` é pinado (`==0.5.0`), como todo runtime dep.** O range aberto `>=0.3.6` atravessava uma mudança de comportamento: em 0.3.x o `Vector` valida a dimensão **no cliente** e levanta `StatementError` (nada chega ao servidor), então o teste de dimensão falharia no piso do próprio range declarado — e o 0.3.x devolve `np.ndarray` na leitura, contradizendo a anotação `Mapped[list[float] | None]`.

**R2a — `app/rag/` materializa os chunks, e NÃO existe splitter.** Esta fatia grava `clause_chunk` a partir do texto que a extração já persistiu: `chunking.py` (funções puras, sem banco) monta o texto e `index.py::index_document(session, document_id)` grava as linhas com `embedding`/`embedding_model` **NULL** — nada chama modelo de embedding aqui, isso é a R2b. A não-existência do splitter é **medida, não pendência**: no corpus persistido (30 documentos) as 4.176 exclusões têm mediana de **101 caracteres**, p99 de 456 e máximo de 907; as 210 regras de franquia têm média de 180. Nada passa de 1.400 — muito abaixo do limite de qualquer modelo de embedding. Então **uma linha de origem = um chunk** e `chunk_index` é sempre **0**; o maior chunk gerado no corpus real tem 934 caracteres (a cláusula de 907 mais o cabeçalho). Cortar por tamanho e sobrepor pedaços seria complexidade sem nenhum texto que a exercitasse — quando o corpus trouxer cláusulas longas, o `chunk_index` já está no schema esperando, e é só o chunking que muda. Contagem no corpus atual: 4.176 + 210 = **4.386 chunks**.

**O texto do chunk carrega significado, não identidade.** O cabeçalho existe porque `"Danos causados por ato doloso"` isolado não diz *de que* aquilo é exclusão — uma exclusão da cobertura de Incêndio e uma exclusão geral da apólice são fatos diferentes, e o vetor precisa saber disso. Os três formatos são curtos de propósito (`Exclusão da cobertura {nome}: …`, `Exclusão geral da apólice: …`, `Regra de franquia da cobertura {nome}: …`): com a cláusula mediana em 101 caracteres, um prefixo longo dominaria o vetor e a busca passaria a ordenar por cabeçalho. **Seguradora, produto e processo SUSEP ficam de fora** — isso é *identidade*, já está em `policy_document` e é respondida por filtro SQL (`WHERE document_id ...`) na hora da busca, com precisão exata e custo zero; dentro do texto só aproximaria todos os chunks da mesma seguradora entre si, ruído que empurra a similaridade para longe do que a pergunta quer. `build_exclusion_text` levanta `ValueError` quando `scope='coverage'` vem sem `coverage_name`: o check do banco garante o *arco*, não o texto, e sem o guard o chunk sairia como "Exclusão da cobertura None" — um texto indexado que mente sobre a própria origem não quebra nada, só responde errado meses depois.

**O invariante da reindexação: texto novo zera o vetor.** O UPSERT é `on_conflict_do_update` sobre os dois índices únicos, e **os índices são PARCIAIS** — então `index_where` (o predicado do índice, `arm.is_not(None)`) tem que vir junto do `index_elements`, senão o Postgres não consegue inferir o árbitro e responde `there is no unique or exclusion constraint matching`. É por isso que há dois UPSERTs, um por braço do arco. No conflito, `text` é sempre atualizado e `embedding`/`embedding_model` passam por um `CASE`: **preservados se o texto é idêntico, zerados se mudou**. Vetor velho sobre texto novo é um índice que *mente* — a busca continua casando pela frase antiga e cita, confiante, uma cláusula que não existe mais; `NULL` significa "ainda não indexado", que é a verdade naquele momento. As duas metades são load-bearing e têm teste cada uma: zerar sempre passaria no teste de invalidação e obrigaria a re-embeddar o corpus inteiro a cada passada (isso é dinheiro), e é o que `test_texto_igual_preserva_o_embedding` trava. Funciona porque no `DO UPDATE` do Postgres **todas as expressões do SET leem a linha antiga** (não são sequenciais), então comparar `clause_chunk.text` com `excluded.text` depois de atribuir `text` continua comparando o valor antigo. **A passada é autoritativa: `index_document` também PODA.** O UPSERT sozinho é idempotente só para origem *adicionada ou alterada*, nunca para origem *removida* — zerar `coverage.deductible_rule_text` (uma re-extração que corrigiu a leitura) deixava o chunk antigo vivo, com o vetor pago intacto, e a busca passaria a citar com confiança uma regra de franquia que o documento não tem mais. O braço das exclusões estava *acidentalmente* protegido (a FK composta impede apagar uma `exclusion` citada por um chunk); o das coberturas não, porque zerar uma coluna de texto não toca em FK nenhuma. `_podar()` apaga, no mesmo `index_document`, os chunks do documento que a passada não produziu. A chave da poda inclui o `chunk_index`, não só o id da origem: hoje o grão é um chunk por origem, mas no dia do splitter uma cláusula que encolhe de 3 pedaços para 2 tem que perder o pedaço nº 2. Pelo mesmo motivo, **texto em branco não vira chunk**: `deductible_rule_text=""` passa pelo filtro `IS NOT NULL` (o schema da extração é `str | None` sem `min_length`, então um LLM que devolve `""` em vez de `null` é persistido tal e qual) e o chunk sairia sendo só o cabeçalho — conteúdo zero, embedding pago na R2b, e um vetor de ruído quase idêntico a todos os outros disputando espaço no HNSW.

`index_document` **não commita** — mesmo contrato de `persist_document`, o chamador é dono da transação (e os statements são Core, então já estão no banco quando a função retorna; não há flush a esperar). `scripts/index_chunks.py` é o CLI (sem argumento indexa tudo, `--document-id N` indexa um) e commita **uma vez, no fim**: um erro no meio desfaz a passada inteira, o que é a escolha certa aqui e não no `run_batch` (lá cada documento já custou dinheiro; aqui repetir é de graça). As linhas por documento saem como `[..]`, não `[ok]` — dizer "ok" antes do commit seria mentira. Verificado no corpus real: 4.386 chunks, e a segunda passada devolve 4.386 de novo.

**R2b — `app/rag/embedding.py` + `embed.py` preenchem os vetores, e esta é a passada que GASTA.** `embedding.py` é o único ponto que fala com a Voyage: `EMBED_MODEL = "voyage-4-lite"`, `MAX_BATCH = 200` (o teto da API é 1000 itens — 200 é menor de propósito, porque cada lote é um commit e uma linha de custo, e um lote gigante que estoura no fim joga fora uma chamada inteira já paga; no corpus atual dá 22 chamadas). `get_client()` lê `VOYAGE_API_KEY` **na chamada**, com `@lru_cache(maxsize=1)` e erro claro se a variável não existe — mesma lição do `DATABASE_URL`: env lida no import mataria a *coleta* do pytest, e falhar no meio da passada significaria lotes já pagos com um 401 genérico como diagnóstico. `embed_documents(texts, client=None) -> (vetores, total_tokens)` valida **antes de qualquer escrita** que cada vetor tem `EMBEDDING_DIM` posições *e* que voltaram tantos vetores quantos textos: a dimensão errada o Postgres barraria de qualquer jeito, mas só depois do lote estar pago e com uma mensagem sobre coluna em vez de sobre modelo; já a contagem o banco **não** barra — um lote curto alinharia vetor com chunk errado no `zip` e o chunk receberia, em silêncio, o vetor do vizinho. Quem chama é `embed_pending` via `asyncio.to_thread` (o SDK da Voyage é síncrono; mesmo arranjo do psycopg3 nos nós do grafo).

**`truncation=False`, contra o padrão do SDK — e o timeout é escolhido, não herdado.** Com `truncation=True` (o padrão da Voyage), um texto maior que o contexto do modelo é cortado **em silêncio**: `clause_chunk.text` guarda a cláusula inteira, o vetor cobre só o começo dela e `embedding_model` diz `voyage-4-lite` como em qualquer linha correta — a busca casa por um prefixo e cita a cláusula toda, que é o "índice que mente" da R2a entrando pela última porta que faltava. Hoje é inalcançável (maior chunk: 934 caracteres), mas a R2a não tem splitter *por decisão medida*, então é este parâmetro que decide, no dia da primeira cláusula longa, entre erro barulhento e índice podre. Junto: `get_client()` passa `timeout=EMBED_TIMEOUT` (60s) em vez de herdar os 600s do SDK, porque `_pendentes` segura as linhas do lote com `FOR UPDATE` durante a chamada inteira — 10 minutos de trava com a transação aberta é exatamente onde o `idle_in_transaction_session_timeout` cobra a conta. `max_retries=0` continua explícito: quem retenta é `_embed_com_retry`, e empilhar a política do SDK por baixo esconderia retentativas em erros que não devem ser retentados.

**Retry só de rate limit, e o silêncio é o inimigo.** `_embed_com_retry` reenvia o lote com backoff exponencial + jitter (6 tentativas, base 20s, fator 2, teto 120s) **apenas** em `voyageai.error.RateLimitError`: é a única falha que se resolve sozinha esperando, porque é uma janela que reabre. Chave inválida ou texto grande demais sobem na hora. **`Timeout` fica de fora por outro motivo, e não por descuido:** um 429 é recusado *antes* de processar, então retentar não paga nada duas vezes; um timeout pode ter sido processado e cobrado do outro lado sem que a resposta chegasse, e reenviar seria uma cobrança em dobro que ninguém detecta depois — melhor a passada morrer e retomar, já que o commit por lote garante que nada pago se perde. Retentar erro real só faz o backfill levar minutos pra dar a mesma mensagem, e mascara a causa. Os números são grandes de propósito (o limite da Voyage é por minuto; esperar 1s só queima tentativa), e o jitter é metade fixa + metade aleatória, pra dois processos que batem no limite juntos não voltarem em fase. Cada espera é logada em **WARNING**, com tentativa e segundos: um backfill de 20 minutos que fica mudo é indistinguível de um travado, e a reação a cada um é oposta. Esgotadas as tentativas a exceção **sobe** — engolir seria pior, porque a passada terminaria "com sucesso" e chunks a menos; o commit por lote já preservou o que foi pago e a re-execução retoma sozinha pelos `embedding IS NULL`. Nos testes o `time.sleep` é monkeypatchado (esperar de verdade custaria ~30s de relógio por teste) e o `FakeVoyage` ganhou `rate_limit_nas_primeiras`; verificado que, sem o wrapper, os dois testes de retry ficam vermelhos (`assert 1 == 6`).

**`input_type="document"` é obrigatório, e é o par que a R3 tem que respeitar.** A Voyage treina o modelo de forma assimétrica: documento e pergunta são embeddados com prefixos diferentes, e o espaço é otimizado pra que uma *pergunta* fique perto dos *documentos* que a respondem, não perto de outras perguntas. A indexação usa `"document"`; a R3 vai consultar com `"query"`. Errar isso **não levanta erro nenhum** — só degrada a recuperação em silêncio —, então o contrato está travado por teste (`test_embed_documents_manda_input_type_document`).

**O preço gravado é o de TABELA, não o efetivo.** `voyage-4-lite` entra no `pricing.json` com `input_per_mtok = "0.02"` e `output_per_mtok = "0"` (modelo de embedding não tem token de saída — é zero por natureza, não por falta de preço). Os primeiros 200M tokens da Voyage são **crédito contra a fatura, não tarifa**: gravar zero destruiria a projeção de custo do corpus, porque "quanto custa re-embeddar tudo?" é uma pergunta sobre a tarifa e o crédito acaba. Verificado no corpus real com `--dry-run`: 4.386 chunks / 796k caracteres / ~199k tokens estimados ≈ US$ 0,004 a preço de tabela.

**`embed_pending` COMMITA POR LOTE — a exceção consciente ao contrato de transação do projeto.** `persist_document` e `index_document` não commitam (o chamador é dono da transação, tudo-ou-nada) porque **repetir aquelas passadas é de graça**: é CPU lendo texto que já está no banco. Aqui cada lote é uma chamada paga, então a fronteira da transação acompanha o **custo de repetir**, não o gosto por atomicidade — uma falha no lote 15 não pode jogar fora os 14 já pagos. Cada lote é commitado junto com a própria linha de `cost_event` (`agent_name="embedder"`, grão = a *chamada*; `request_id`/`client` ficam `NULL` porque a passada é offline, mesma convenção da extração), e a re-execução retoma de onde parou: as linhas commitadas não voltam no `embedding IS NULL`. O lote é buscado a cada volta (`LIMIT n` sobre o filtro) em vez de fatiar uma lista carregada no início — a query "próximas N pendentes" *é* o cursor, sem offset pra desalinhar.

**Trocar `EMBED_MODEL` não pode ser um no-op silencioso — a passada se RECUSA a rodar.** As linhas já embeddadas nunca voltam ao filtro `embedding IS NULL`, então apontar `EMBED_MODEL` pra um sucessor de mesma dimensão e rodar preencheria só os `NULL` (e todo chunk cujo texto a R2a rezerou): o HNSW ficaria com vetores de **dois modelos**, cujas distâncias de cosseno não são comparáveis, e a busca devolveria vizinhos errados sem erro nenhum — o mesmo "índice que mente" da R2a, entrando por outra porta. `embedding_model` existe exatamente pra essa pergunta ser respondível, e agora alguém a faz: `contar_desatualizados()` conta as linhas com vetor de outro modelo e `embed_pending` levanta `ValueError` **antes da primeira chamada paga** se houver alguma. A saída é `remodel=True` (`--remodel` no CLI), que inclui essas linhas na passada e devolve o índice à consistência; é opt-in porque re-embeddar o corpus é gasto, e gasto não se faz por efeito colateral.

**O lote é reivindicado com `FOR UPDATE SKIP LOCKED`.** Sem trava, duas passadas simultâneas (dois operadores, ou uma re-execução disparada antes da primeira terminar) leem os mesmos ids, pagam as duas pelo mesmo texto e gravam duas linhas de `cost_event` — dinheiro em dobro dentro do livro-caixa que o projeto inteiro existe pra manter confiável. A trava dura **o lote**, não a passada, acompanhando o commit por lote. O custo consciente disso é que a transação fica aberta durante a chamada HTTP e durante o backoff de rate limit: num Postgres com `idle_in_transaction_session_timeout` ligado (o Postgres puro vem com ele desligado; alguns gerenciados não) é aí que se paga a conta, e a alternativa — uma coluna de *claim* commitada antes da chamada — é migration. `pending_stats` **não** trava: é leitura pura, e travar linhas num `--dry-run` bloquearia a passada de verdade. Efeito colateral consciente do `SKIP LOCKED`: se tudo que resta estiver travado por outro processo, o lote volta vazio e a passada termina cedo — está certo, o outro processo está cuidando delas.

**O `--remodel` não carrega o vetor que vai sobrescrever.** `_pendentes` traz as linhas com `defer(ClauseChunk.embedding)`: `embedding` é a única coluna que a passada nunca *lê*. No caminho normal isso não custaria nada (as pendentes têm `NULL` ali), mas `--remodel` é justamente o que varre o corpus inteiro **com** vetor preenchido — seriam 1024 floats por linha vindos do banco só pra serem descartados (~18 MB no corpus atual, crescendo linear). Atribuir a um atributo adiado não dispara carga, então a escrita não muda. O teste inspeciona só a lista de colunas do SQL (o trecho antes do `FROM`): o `WHERE embedding IS NULL` cita a mesma coluna e faria uma busca no SQL inteiro dar falso vermelho.

**O CLI valida `--limit`/`--batch-size` no `main()`, antes de tocar no banco — e `embed_pending` valida os dois de novo.** A validação dupla é de propósito: `limit=0` sai pelo `while` na primeira volta e devolve `{"chunks": 0, ..., "cost_usd": 0}`, um relatório indistinguível de "já estava tudo indexado", e quem chama de fora do script (teste, notebook, a ferramenta da R3) não passa pelo `argparse`. `--limit 0` viraria `LIMIT 0`, faria `pending_stats` devolver zero e o script imprimiria *"nenhum chunk pendente — tudo já tem vetor"* com o corpus inteiro por indexar: mentira plausível é a pior saída possível num script que gasta dinheiro. `--batch-size 0` estourava num `ZeroDivisionError` da conta de lotes previstos, antes do guard de `embed_pending` conseguir falar; e `--batch-size` acima de `MAX_BATCH_API` (1000) só falharia depois do plano impresso, na resposta da API.

**O teste da fronteira precisou de um `db_session` próprio, e isso é o detalhe que quase produziu um falso verde.** O `db_session` do `conftest.py` liga a Session a uma Connection que já está numa transação simples, e o SQLAlchemy 2.0 resolve `join_transaction_mode="conditional_savepoint"` como **`rollback_only`** nesse caso: `session.commit()` vira **no-op** e `session.rollback()` derruba a transação inteira. Sob esse regime, commit por lote e commit único no fim são literalmente indistinguíveis. `tests/test_embed.py` sobrescreve o fixture abrindo um `begin_nested()` antes de criar a Session, o que muda o modo pra `create_savepoint`: cada commit libera um SAVEPOINT (durável dentro da transação externa) e o rollback volta só até o último. Verificado: com commit único no fim, `test_falha_no_segundo_lote_preserva_o_primeiro` fica **vermelho** (`assert 0 == 2` — nenhum chunk sobrevive) e os outros 7 testes do módulo continuam verdes, que é exatamente o que faz dele o único guarda dessa decisão.

**O que os testes da R2b provam** (`tests/test_embedding.py` sem banco, `tests/test_embed.py` com): `input_type`/modelo enviados; lista vazia não vira chamada; dimensão errada e contagem errada rejeitadas antes de tocar no banco; `get_client` sem chave (e com chave vazia) falhando alto; só as linhas `NULL` são preenchidas; uma linha de custo por **lote**, com `cost_usd` batendo com `app.cost.cost_usd`; a fronteira de transação; e a **segunda passada como no-op provada por contagem de chamadas ao cliente falso** (`segundo.calls == []`), não por comparação do banco — uma versão que re-embeddasse tudo e regravasse vetores idênticos deixaria o banco igual e a fatura maior. O `FakeVoyage` mora em `tests/test_embedding.py` e é importado pelo outro módulo (mesmo padrão de `tests/test_index.py` importando de `test_persist.py`); é determinístico e nunca sai da máquina — **nenhum teste gasta dinheiro**.

**R3a — `app/rag/search.py::search_clauses` busca por similaridade.** Esta fatia entregou função + teste, sem tocar em `app/agents/`; quem a liga ao grafo é a R3b (seção logo abaixo). A assinatura é `search_clauses(session, question, *, k=5, max_distance=None, document_ids=None, client=None) -> list[Hit]`, e o `Hit` é um dataclass `frozen` que carrega `chunk_id`, `document_id`, **os dois braços do arco** (`exclusion_id`/`coverage_id`, exatamente um preenchido), o texto e a distância — a origem viaja junto porque uma cláusula recuperada sem procedência é só uma frase, e citar a fonte é o motivo de as FKs do arco existirem. O `ORDER BY` usa `cosine_distance` (o operador `<=>`), que é a **mesma métrica do índice** (`vector_cosine_ops`): trocar por L2 continua devolvendo resultados, só que por seq scan + sort — verificado no corpus real com `EXPLAIN` (ver o comando na seção de comandos).

**`embed_query` é o outro lado do par assimétrico, e `_embed_com_retry` virou o ponto único.** Indexar usa `input_type="document"`, buscar usa `input_type="query"`; a Voyage otimiza o espaço pra que a *pergunta* caia perto dos *documentos que a respondem*, e usar o mesmo dos dois lados não levanta erro nenhum — só piora os vizinhos em silêncio, que é a razão de os dois lados estarem travados por teste. `input_type` passou a ser parâmetro de `_embed_com_retry` (em vez de constante fixa) para que a busca herde de graça o retry só-de-rate-limit, o `truncation=False` e o timeout escolhido. A validação (dimensão + correspondência 1:1) saiu para `_validar` e é compartilhada. **Existem duas funções de query de propósito**: `embed_query(text) -> list[float]` é a assinatura simples, e `embed_query_with_tokens(text) -> (vetor, tokens)` é o que a busca usa — o `cost_event` precisa do número que a **API cobrou**, e estimar tokens por contagem de caracteres gravaria custo errado com cara de certo, exatamente o que o fail-loud do `app/cost.py` existe pra impedir. **A busca tem orçamento de espera próprio nas DUAS pontas — tentativas e timeout —, e o timeout é o que de fato limita.** `RATE_LIMIT_TENTATIVAS_QUERY = 2` (espera inicial 2s, contra 6 tentativas e 20s do backfill) existe porque `tentativas`/`espera_inicial` viraram parâmetros de `_embed_com_retry`: quem espera define o orçamento — o backfill é offline e pode dormir minutos, a busca roda dentro de um request e segura um worker do `asyncio.to_thread` enquanto dorme. Só que cortar tentativas **não limitava a latência**: `get_client()` é cacheado sem argumento, então a busca herdava o `timeout=60s` escolhido pra um lote de 200 textos sob `FOR UPDATE`, e uma Voyage travada segurava o worker 60s por chamada (até ~120s com o retry). Daí `get_query_client()`, um segundo cliente cacheado com `EMBED_TIMEOUT_QUERY = 10s` — o timeout é parâmetro do *cliente*, não da chamada, então dois caminhos com paciências opostas exigem dois clientes. Com algumas buscas simultâneas nesse regime o executor padrão esgota, e aí travam também as chamadas síncronas ao Postgres dos outros nós do grafo. Os dois lados têm teste, e o load-bearing é o que prova que `embed_query` **usa** o cliente curto: ter o cliente e não usá-lo passaria despercebido. Os dois lados do par ficam travados em `tests/test_embedding.py` (um teste por `input_type`), junto com a dimensão validada também no caminho da query — ali não há coluna do Postgres pra reclamar depois: um vetor do tamanho errado só apareceria como *"different vector dimensions"* dentro do `<=>`, no meio de uma busca.

**`hnsw.ef_search` é um teto silencioso, e a busca ajusta ele por transação.** O default do pgvector é **40** candidatos varridos: com o índice em uso, um `LIMIT 100` volta com **40 linhas e nenhum erro** — verificado no corpus real (4.386 chunks) forçando `enable_seqscan=off`; com `SET LOCAL hnsw.ef_search = 100` o mesmo plano devolve 100. Hoje, nesse tamanho, o planner ainda prefere seq scan e o resultado sai exato, o que é justamente o perigo: a garantia de "`k` resultados" ficaria dependendo de uma escolha de plano que muda sozinha quando a tabela cresce. Pior no caminho filtrado — o `WHERE document_id` é aplicado **depois** da varredura aproximada, então dos ~40 candidatos globais sobram só os do recorte (com 29 documentos, ~1). Por isso `search_clauses` emite `hnsw.ef_search = min(max(4k, 40), 1000)` antes do SELECT: acompanha o `k`, piso no default e teto no máximo que o pgvector aceita.

**Mas `ef_search` sozinho NÃO cobre o caso filtrado — e é o filtrado que quebra.** O `WHERE` (`document_id`, `embedding_model`, `IS NOT NULL`) é aplicado **depois** da varredura aproximada, então dos ~40 candidatos globais sobram só os que passam. Medido: forçando o plano do HNSW no corpus real, `k=5` com `document_ids` de um documento devolveu **1 linha**; com `hnsw.iterative_scan` ligado, 5 de 5. E esticar `ef_search` por um fator fixo não conserta, porque a diluição é a **seletividade do filtro** (29 documentos ⇒ ~29×), não um múltiplo do `k` — o fator 4, no `k` padrão de 5, dava `max(20, 40) = 40`, exatamente o default do pgvector, ou seja, não fazia nada. `hnsw.iterative_scan = strict_order` existe pra isso: o índice devolve mais lotes até juntar `LIMIT` linhas que sobrevivam ao filtro. **`strict_order` e não `relaxed_order`** porque aqui a ordem por distância *é* o resultado — o limiar corta pelas primeiras posições, e "quase ordenado" vira hit descartado à toa. Ligado **sempre**, não só com `document_ids`: o filtro de modelo dilui igual num corpus meio remodelado, e sem filtro o primeiro lote já satisfaz o `LIMIT`, então não custa nada.

Os dois parâmetros vão num `select(func.set_config(..., is_local=True))` — `SET LOCAL` em forma de função: mesma vida útil (morre no fim da transação, não vaza pra outras conexões), uma ida só ao banco, e **aceita bind param**, coisa que a sintaxe `SET` não aceita (a primeira versão interpolava o `int` na string). Os testes não conseguem ver o truncamento (4 chunks ⇒ seq scan sempre), então travam o que dá: `SHOW hnsw.ef_search` e `SHOW hnsw.iterative_scan` **depois** da busca, na mesma transação.

**Só vetores do modelo atual entram no ranking.** `embed_pending` commita por lote de propósito, então um `--remodel` interrompido (rate limit esgotado, Ctrl-C) deixa metade do corpus num modelo e metade no outro — e distâncias de cosseno de modelos diferentes não são comparáveis. Sem filtro, a busca ordenaria os dois espaços juntos e devolveria vizinhos errados **sem erro nenhum**: o mesmo "índice que mente" que `contar_desatualizados` guarda do lado da *escrita*, entrando pelo lado da *leitura*, que estava aberto. Daí o `WHERE embedding_model = EMBED_MODEL`. O efeito colateral é consciente e está no docstring: com o corpus meio remodelado a busca devolve menos (ou nada) em vez de devolver errado — vazio é recuperável rodando o `--remodel` até o fim, ranking errado com cara de certo não é.

**A busca sempre devolveria `k` — a lista vazia é produzida SÓ pelo limiar** (e pela ressalva do modelo, acima). Não existe "não encontrei" numa busca vetorial: o `LIMIT k` entrega os k vizinhos menos distantes do corpus inteiro ainda que o melhor deles esteja do outro lado do espaço, então "minha bicicleta foi roubada na rua" volta com 5 cláusulas de seguro residencial e um sintetizador confiante transforma isso numa resposta errada **com citação**. O limiar (`max_distance`) é o que permite dizer "não sei", e o docstring afirma isso explicitamente porque é o tipo de propriedade que quem lê a assinatura assume ao contrário. O corte roda **depois do `LIMIT`**, não como `WHERE distance <= :max`: é corte de relevância, não paginação — no SQL faria a query cavar mais fundo atrás de k linhas que passassem (mais trabalho pro mesmo resultado) e esconderia dos testes e da calibração as distâncias descartadas.

**`MAX_DISTANCE_PADRAO = 0.60`, decidido mas ainda não medido, e NÃO aplicado por padrão** (`max_distance=None` = sem corte — quem quer cortar passa o valor explicitamente; enquanto o número não estiver validado, cortar em silêncio seria descartar resultado sem o chamador ter pedido). Quem mede é `scripts/calibrate_search.py`, que roda a busca sem limiar sobre `data/eval/search_questions.txt` (10 perguntas em escopo, 5 fora) e imprime, por pergunta, as distâncias do 1º/3º/5º hit, e no fim a média do 1º hit por grupo mais **a maior distância `+` contra a menor `-`** — é ali que o limiar mora. Se os grupos separam, qualquer valor no meio serve; se cruzam, nenhum corte por distância os separa e isso também é resultado (o filtro teria que vir de outro lugar). **A composição do arquivo é parte do teste, não enfeite.** Os `-` são de dois tipos: assunto totalmente fora (receita de bolo, imposto de renda) e **seguro de outro ramo** (vida, viagem, cirurgia estética) — só o segundo tipo mede alguma coisa, porque um limiar que barra o bolo pode estar separando vocabulário em vez de assunto, e quem escreve pro sistema escreve em linguagem de seguro. Do outro lado, bicicleta guardada dentro de casa e carro na garagem são `+` de propósito: as CGs residenciais falam dos dois, então são justamente as perguntas que *parecem* de outro ramo e não são — rotulá-las como fora de escopo empurraria o limiar pra baixo e ensinaria o sistema a dizer "não sei" pra pergunta que ele sabe responder. Calibrar de verdade e fixar a constante **continua pendente** — o script existe, o número não. O script dá `rollback()` a cada pergunta: `search_clauses` abre transação (o `set_config` local) e não fecha, e sem isso a conexão ficaria `idle in transaction` durante todas as chamadas HTTP seguintes — exatamente onde um Postgres com `idle_in_transaction_session_timeout` derruba a sessão no meio, com os embeddings já pagos. Pelo mesmo motivo ele imprime progresso linha a linha: a tabela só sai no fim (precisa da largura máxima), e uma passada que morre no meio não pode sair muda depois de ter gasto.

**A busca grava `cost_event` com `agent_name="rag_search"`, e é a primeira coisa da R3 que roda dentro de um request.** Daí `request_id`/`client` virem dos ContextVars, como nos nós do grafo — o oposto da passada de indexação (`agent_name="embedder"`), que é offline e grava os dois como `NULL`. A gravação é **best effort** (log de warning e segue), pelo mesmo motivo do `_record_cost` do grafo: quando chegamos ali a chamada já foi paga, e perder uma linha de observabilidade é muito mais barato do que derrubar um request que já gastou. Detalhe conhecido e consciente: uma pergunta tem ~6 tokens, que a US$ 0,02/Mtok dá 1,2e-7 e **arredonda pra zero** em `Numeric(12, 6)` — o número verdadeiro e somável da recuperação é `input_tokens`, não o `cost_usd` por linha.

**`document_ids` filtra ANTES do ranking, e a lista vazia curto-circuita.** Restringir a um documento é *identidade* (seguradora, produto, processo SUSEP), que a R2a deixou de fora do texto do chunk justamente porque um `WHERE` responde isso com precisão exata e custo zero. `document_ids=[]` significa "nenhum documento" e devolve `[]` **sem chamar a API** — o recorte é vazio, a resposta não depende do vetor, e a chamada seria paga por nada. `k < 1` levanta `ValueError` antes da chamada paga: `LIMIT 0` devolveria `[]`, indistinguível da única lista vazia legítima da função (a do limiar).

**Os testes plantam os vetores à mão** (`tests/test_search.py`), em duas dimensões do vetor de 1024: pergunta em `(1,0)`, chunks em `(1,0)` / `(1,1)` / `(0,1)` / `(-1,0)`, o que dá distâncias 0 / ~0,293 / 1 / 2 calculáveis de cabeça. O que se prova é a **mecânica** da recuperação — amarrar isso à saída de um modelo real tornaria o teste dependente de semântica que nem roda ali. Dois detalhes são load-bearing: os vetores são plantados **fora da ordem de id**, senão um `ORDER BY` ignorado (ou trocado por ordem de inserção) passaria verde; e o teste de `document_ids` põe o vizinho **mais próximo** no outro documento e depois confere, numa busca sem recorte, que ele era mesmo o primeiro colocado — sem essa segunda metade, um filtro que não filtrasse nada e uma geometria que já excluísse o chunk seriam indistinguíveis. O fixture de limpeza de `cost_event` é **autouse** porque toda busca grava uma linha commitada em transação própria, fora do alcance do rollback do `db_session`, e ela vazaria pro `tests/test_cost.py`, que conta a tabela inteira.

**R3b — o `rag_worker` entra no grafo, e o supervisor passa a ter TRÊS rotas.** `SupervisorDecision.next` virou `Literal["sql_worker","rag_worker","unsupported","END"]`. O corte entre os dois workers é **estrutura × teor**: contar, filtrar ou comparar campo categórico ("quantas seguradoras cobrem vendaval?") é SQL; o que se responde lendo o texto de uma cláusula ("em que situações o roubo não é coberto?") é RAG. `WORKERS` (frozenset) é o conjunto dos destinos que são **nó de verdade**; `"unsupported"` fica fora dele de propósito — é classificação, não worker, e sai pelo synthesizer como qualquer outro fim de grafo. Por isso `route()` devolve `END` tanto pro `"END"` (hoje só fail-safe do enum) quanto pro `"unsupported"` (e pro valor inválido, com o print de fail-closed): **route decide o CAMINHO, o synthesizer decide a FRASE**, lendo `state["next"]`. O `path_map` do `add_conditional_edges` ganhou `"rag_worker"` e continua mandando `END → "synthesizer"`; `add_edge("rag_worker", "synthesizer")` fecha o caminho como no SQL worker — direto, sem passar de novo pelo supervisor (ver o parágrafo do single-hop abaixo).

**Duas regras estão no prompt do supervisor porque as duas falhas são silenciosas.** (1) **"Não cobre" é resposta, não pergunta fora de escopo.** "Enchente é coberta?" se responde com a *cláusula de exclusão* de enchente, que existe no corpus — classificar isso como `unsupported` recusa uma pergunta que o sistema sabe responder, e o usuário não tem como saber que a recusa foi um erro de roteamento. É a mesma distinção que a composição de `data/eval/search_questions.txt` já carrega (bicicleta guardada em casa e carro na garagem são `+`, porque as CGs residenciais falam dos dois). (2) **Na dúvida, `rag_worker`.** A assimetria é grosseira e está escrita no prompt: recusar errado custa a resposta certa a quem tinha pergunta legítima; buscar à toa custa ~6 tokens de embedding (frações de centavo) e devolve "não encontrei".

**O `rag_worker` é o único nó que NÃO chama a Anthropic.** Ele pega a última `HumanMessage`, abre a **própria sessão** (`SessionLocal`, mesma razão do `record_call_cost`: o nó não conhece a borda HTTP e não recebe session por parâmetro) e chama `search_clauses(k=RAG_K)` — **sem `max_distance`**, aplicando o corte ele mesmo sobre o que voltou. O import de `app.db` é local pelo mesmo motivo do de `app/cost.py` — resolve `SessionLocal` na hora da chamada, que é o que faz o `monkeypatch.setattr("app.db.SessionLocal", ...)` dos testes pegar. A única chamada paga é o embedding da pergunta, dentro da busca (que grava o próprio `cost_event` como `rag_search`); virar isso em frase é trabalho do synthesizer. **O limiar é aplicado aqui e não é opcional**: `search_clauses` sempre devolveria `k` vizinhos, então sem corte uma pergunta que escapou do supervisor volta com 5 cláusulas residenciais e o synthesizer as transforma em resposta errada *com citação*. **O corte é do nó, e não do `max_distance` da busca, pra que o descarte seja visível**: é a mesma operação (a R3a já corta depois do `LIMIT`), mas com o limiar dentro da busca as distâncias reprovadas somem — e são exatamente elas que dizem se `MAX_DISTANCE_PADRAO` está no lugar certo, num número que segue *decidido e não medido*. Quando o corte esvazia a lista, a melhor distância vai pro log em INFO: sem isso, "não achei nada" e "achei e cortei a 0,61" ficam indistinguíveis justamente no caso que precisa de diagnóstico.

**O grafo é SINGLE-HOP, e a terminação é ESTRUTURAL — foi a correção mais cara desta fatia.** Os workers vão direto pro synthesizer (`add_edge("sql_worker", "synthesizer")` e idem pro RAG); nenhuma aresta volta pro supervisor, então ele roda **uma vez por request**. Antes voltavam, e a medição num `/ask` real mostrou o preço: o supervisor re-classificava a mesma pergunta a cada volta, reroteava pro mesmo worker e só parava no circuit breaker — **10 chamadas de LLM onde bastavam 3**, com o supervisor consumindo **8.790 tokens contra 4.204 do worker** que de fato fez o trabalho, e na rota RAG **4 embeddings pagos, 3 jogados fora**. A tentativa anterior foi uma instrução de prompt ("se um worker já respondeu, escolha END"): ela reduz a *chance* do laço, não o *custo do caso ruim* — pedir pro modelo não repetir é mais frágil do que não lhe dar a chance. O que se perde é o multi-hop: uma pergunta composta ("quantas seguradoras cobrem vendaval **e** o que a cláusula diz da franquia?") hoje é respondida por um worker só. Isso é **fatia própria**, e é exatamente a razão de a aresta não voltar: multi-hop exige uma regra de parada explícita (quem decide que já basta, e com base em quê), e herdar o ciclo "de graça" é como se chegou às 10 chamadas.

Cada hit sai numa linha com `chunk_id`, `document_id` e a distância (`_formatar_hits`) — os ids são o que torna a citação possível rio abaixo, e a distância é o que distingue, na leitura do histórico, um apoio forte de um vizinho que passou raspando. Falha de busca vira **mensagem**, não exceção, mesmo contrato do `sql_worker` — e desde a fatia da falha interna essa mensagem é marcada por `name="worker_error"` e não carrega nada da exceção (ver a seção "Exceção de worker não chega ao usuário", abaixo). **O `.strip()` no texto do hit ficou DEFENSIVO com o single-hop, e o histórico importa pra ninguém removê-lo achando que é enfeite.** Ele foi escrito quando o grafo era cíclico: a mensagem do worker voltava pro supervisor como último turno `assistant`, e a API recusa com **400** um turno assistente final terminando em espaço em branco — `clause_chunk.text` guarda a cláusula como a extração devolveu (PDF lido por LLM, que termina em `\n` com facilidade) e a R2a só rejeita texto *em branco*. Hoje essa mensagem só é lida pelo synthesizer, dentro de um turno `user`, onde espaço no fim é inofensivo; o strip fica porque volta a ser load-bearing no dia do multi-hop — que é justamente quando ninguém vai lembrar — e porque texto normalizado é o certo de qualquer jeito. A mensagem de erro tinha o mesmo `.strip()` pelo mesmo motivo, e ele **saiu junto com o texto da exceção**: o conteúdo agora é uma constante montada só com o nome do nó, então não há mais como terminar em espaço em branco (o teste que provava isso deu lugar a um que fixa a esterilidade do conteúdo — `tests/test_falha_interna.py`).

**O prompt do synthesizer rotula o payload como "Resultado do worker", não "da query".** Com dois workers no grafo o conteúdo tanto pode ser linha de `SELECT` quanto cláusula recuperada, e chamar cláusula de resultado de query faz o modelo escrever "a consulta retornou 2 registros" sobre uma consulta que nunca rodou — além de brigar com a instrução, no mesmo prompt, de não repetir os identificadores técnicos.

**As QUATRO frases finais são coisas diferentes, e trocá-las é mentir de um jeito plausível.** Cada uma responde a uma pergunta diferente do usuário sobre o que aconteceu:

| frase | significado | o que aconteceu | tem traceback no log? | declara base? |
|---|---|---|---|---|
| `NO_ANSWER` | "eu deveria conseguir e falhei" | nenhum worker produziu resultado **e nada quebrou** — supervisor devolvendo `END`/valor inválido, ou circuit breaker. Falha de **roteamento**, nossa, e vale tentar de novo | não | não — ninguém consultou nada |
| `NADA_RELEVANTE` | "eu procurei e o corpus não tem" | a busca rodou e todos os vizinhos ficaram acima do limiar. Fato sobre o **corpus** | não | **sim**, a base PESQUISÁVEL (menor que o corpus) — sem ela a frase lê como "isso não existe" em vez de "não achei nas que eu tenho" |
| `FORA_DE_ESCOPO` | "eu não trato desse assunto" | o supervisor classificou antes de gastar qualquer coisa. Fato sobre o **sistema**, e reformular a pergunta não muda nada | não | não — a frase é sobre o escopo, e nada foi aberto |
| `FALHA_INTERNA` | "algo quebrou do nosso lado" | um worker levantou exceção (banco fora, API de embedding recusando, payload malformado). Fato sobre a **infraestrutura**: nada a ver com a pergunta | **sim** | não — a consulta não rodou, e o rodapé daria ar de completude à única frase que significa o contrário |

Nenhuma das quatro chama LLM — todas entram pela regra do `NO_ANSWER` ("não se paga pra reescrever uma frase que já está pronta"), e no caso do `NADA_RELEVANTE` mandar o vazio pro sintetizador ainda arriscaria ele inventar um "mas talvez…" em cima de nada. A última coluna é a diferença operacional que separa `FALHA_INTERNA` de `NO_ANSWER`, que de fora são as duas "problema nosso": uma sempre tem um incidente correspondente pra investigar, a outra não tem nenhum — trocá-las manda o operador procurar um traceback que não existe, ou ignorar um que existe. A lista vazia da busca vira mensagem **explícita**, nunca string vazia: mensagem em branco no histórico é indistinguível de "o worker não rodou", e a resposta degradaria de "procurei e não achei" pra "falhei".

**A resposta declara sua BASE, e o rodapé é montado em CÓDIGO — o prompt do synthesizer não menciona base nenhuma.** `_com_base(frase, sufixo)` é o único ponto que junta os dois (separador `\n\n`: o rodapé é um bloco à parte, não uma oração da resposta), e o sufixo é determinístico — número contado em Python colado numa string fixa. Pedir a declaração ao LLM seria pedir pra ele *afirmar quantos documentos consultamos*: exatamente o tipo de número que ele inventa com confiança quando não está no payload e reescreve quando está, e uma declaração de cobertura errada é **pior do que nenhuma**, porque dá ao usuário uma razão falsa pra confiar na resposta. Por isso a frase vem do modelo e o rodapé vem do código, e há teste dos dois lados (`SYNTHESIZER_SYSTEM` não contém a palavra "base"; o `system` e o payload que o synthesizer manda não contêm o rodapé que aparece na resposta).

**São TRÊS bases, porque três coisas diferentes são afirmadas — e a diferença entre elas é o que impede o rodapé de mentir.** (1) A rota SQL agrega sobre as tabelas inteiras, então a base dela *é* o corpus: `Base: {n} apólice(s) analisada(s).`, com `n` vindo de um `count(*)` em `policy_document` (`_base_do_corpus`). (2) A rota RAG responde lendo `k` cláusulas de `d` documentos, e é isso que a resposta cobre: `Base: {k} cláusula(s) de {d} apólice(s).` — declarar o corpus ali implicaria que as apólices foram lidas inteiras quando algumas cláusulas foram. (3) O `NADA_RELEVANTE` declara a base **PESQUISÁVEL**: `Base: {n} apólice(s) pesquisada(s).`, contada por `contar_documentos_pesquisaveis`. Esta terceira existe porque a busca semântica só alcança chunk com vetor **do modelo atual** — um documento extraído e ainda não embeddado (o intervalo normal até `scripts/embed_chunks.py` rodar), ou meio corpus num `--remodel` interrompido, está na base e fora do alcance. Usar a contagem do corpus ali diria "procurei em 40" quando 30 foram procuradas, inflando justamente a frase cujo trabalho inteiro é dizer "não achei NAS QUE EU TENHO". A contagem mora em `app/rag/search.py`, ao lado da busca, e as duas compartilham o predicado `_filtro_pesquisavel()`: uma cópia do filtro em outro módulo divergiria no dia em que a busca ganhasse mais uma condição, e o número passaria a descrever um recorte que a busca não faz mais.

**As duas contagens contam PRODUTOS (`distinct susep_process`), não linhas.** O grão de `policy_document` é `(susep_process, version)` — está no `UniqueConstraint` da tabela — e `scripts/susep_harvest.py --all-versions` existe pra baixar o histórico completo de cada processo. Num corpus assim, três versões do mesmo produto virariam "3 apólices" num rodapé que o usuário lê como três seguradoras diferentes; o produto é o processo SUSEP, e a versão é a mesma apólice registrada de novo. As duas têm que contar a **mesma unidade**: se uma contasse versão e a outra produto, a diferença entre elas deixaria de significar "o que ainda não foi embeddado" e viraria ruído. O corpus de teste tem 5 linhas para 4 produtos, e 3 linhas alcançáveis para 2 produtos — as sobreposições existem justamente pra que contar linha e contar produto deem números diferentes.

**Sem denominador.** A versão anterior fechava com "de 138 elegíveis", e o 138 não se sustenta: ele existia só na prosa do README e **não é derivável do manifesto** — `data/corpus/corpus_manifest.json` tem 147 processos, 143 com ao menos uma versão residencial, 141 com versão vigente residencial. Um denominador não verificável é o pior conteúdo possível pra um rodapé que existe pra ser confiável, e nada no repositório notaria a defasagem quando a SUSEP registrasse ou retirasse um produto. Se o número voltar um dia, tem que voltar derivado de algo que o repositório saiba contar.

**Quem declara a base é o WORKER, na própria mensagem, e a ausência de declaração significa "sem rodapé".** O worker é quem consultou, então é ele quem sabe *se* consultou e *o que* a consulta cobriu; o synthesizer só lê `AIMessage.additional_kwargs[BASE]` e traduz. Campo **estruturado da mensagem que já carrega o resultado**, pelo mesmo motivo de `WORKER_ERROR` ser o `name` e não um prefixo mágico no conteúdo — a alternativa seria o synthesizer contar de volta as linhas de `_formatar_hits`, amarrando a declaração de base ao formato de um texto que existe pra ser lido por um LLM. Não é campo do `State` de propósito: é fato sobre *uma consulta*, não sobre o grafo. **O default fail-closed é a decisão, não um detalhe:** o desenho anterior dava o rodapé do corpus a quem não dissesse nada, o que fazia da saída insegura a padrão — bastava um worker novo entrar em `WORKERS` esquecendo a chave pra que toda resposta dele afirmasse que o corpus inteiro foi lido, sem erro e sem teste vermelho. Rodapé a menos é resposta sem procedência; rodapé a mais é afirmação falsa de cobertura, que é o único erro que este rodapé não pode cometer. Os dois branches (chave ausente e `tipo` desconhecido) têm teste. **`_sufixo_da_resposta` é o ÚNICO caminho pra um rodapé**, inclusive no `NADA_RELEVANTE`: a primeira versão chamava `_sufixo_pesquisado()` direto naquele branch, o que reintroduzia o fail-open por outra porta — a frase declarava a base **global** independentemente do que o worker varreu, e `search_clauses` já aceita `document_ids`, então no dia do recorte por documento ela diria "procurei em 30" com 1 procurado. Enquanto a busca for global os dois caminhos dão o mesmo número, então nenhum teste de ponta a ponta os distingue: quem trava isso é um teste estrutural, com uma mensagem de `NADA_RELEVANTE` que não declarou nada e portanto não pode ganhar rodapé.

**`k` e `d` são contados DEPOIS do corte por distância.** Contar sobre `hits` (o que a busca trouxe) em vez de `relevantes` (o que sobrou do limiar) inflaria as duas metades de uma vez — "3 cláusulas de 3 apólices" numa resposta escrita em cima de 2 cláusulas de 2 documentos —, e o erro é do tipo que faz a resposta *parecer mais apoiada do que é*, o oposto do que o rodapé existe pra fazer.

**Erro de query não declara base.** `run_query` devolve como TEXTO tanto as linhas quanto as recusas do guard e o erro do Postgres — é o contrato que faz SQL inválido ser reportável em vez de fatal. Só que "houve mensagem" não é "houve consulta": num `UndefinedColumn` o SELECT não leu apólice nenhuma, o synthesizer parafraseia o erro ("não consegui obter essa informação") e um rodapé embaixo disso afirmaria uma verificação que não houve. O `sql_worker` só preenche a declaração quando `rows` não começa por `ERRO_PREFIXO` — **constante exportada pelo `mcp_servers/postgres_mcp_server.py`**, usada nas quatro saídas de erro de lá, e não um `startswith("Error")` escrito do lado de cá: produtor e leitor não podem divergir. Não colide com resultado, que sempre começa em `"Columns: "`.

**Montar a base é BEST EFFORT de ponta a ponta, como `_record_cost`.** As duas contagens passam por `_contando`, que abre sessão própria e devolve `None` em qualquer falha (log de warning) — a resposta sai **sem rodapé** em vez de estourar: quando chegamos ali a pergunta já foi paga e já tem resposta, e trocá-la por um 500 destruiria o que já se comprou; inventar um número seria pior, porque o rodapé só serve se for confiável. `_sufixo_da_resposta` guarda os **dois subscritos** do braço recuperado, e só eles: eles leem um dicionário montado em **outro nó**, e um `KeyError` ali escaparia do synthesizer — o *último* nó — abortando o grafo e devolvendo 500 num request que já tem a resposta na mão. O `try` é estreito de propósito; envolver também as chamadas de contagem (que `_contando` já protege inteiras) faria um defeito real no caminho do corpus sair como *"declaração malformada"*, mandando o operador caçar um payload de worker que não existe. (`_contando` é também o ponto único que os testes sem banco desligam, no lugar de patchear cada sufixo.) O rodapé entra no caminho **degradado** do synthesizer (`frase or resultado`) também: o que foi consultado não muda quando a síntese cai, e um despejo cru sem procedência é ainda menos interpretável.

**Limitação conhecida, e ela cobra no dia do multi-turno:** o rodapé é gravado dentro do `content` da mensagem `final`, ou seja, dentro do histórico. Hoje é inócuo (o `/ask` monta um State novo por request), mas na superfície de WhatsApp o supervisor converte o histórico inteiro em turnos, e o número que este desenho mantém **fora** do contexto do modelo volta pra dentro como texto de assistente — de onde dá pra parafrasear, arredondar, ou carregar pra um turno em que worker nenhum rodou. A saída é o rodapé viajar fora do `content` (em `additional_kwargs`, com a junção na borda HTTP), e ela é da fatia do multi-turno porque é lá que se decide o que o supervisor enxerga do histórico. Está anotado no código, no ponto onde o rodapé é colado.

**Nos testes, as contagens são desligadas com no-op explícito em todos os módulos do grafo menos um** — mesma forma e mesmo motivo do no-op de `record_call_cost`, e o patch é no seam único (`_contando`) pra que uma terceira base não reintroduza a dependência sem ninguém notar: contar exige banco, e uma asserção sobre o *texto* da resposta não pode depender de quantos documentos outro módulo deixou commitados (sem o no-op, `tests/test_ask.py` passava a devolver "Base: 0 apólice(s)" assim que a suíte rodasse depois de um módulo que sobe o container — verificado). O rodapé da rota RAG **não** é desligado: ele sai dos próprios hits, sem tocar no banco.

Quem exercita o contrato de verdade é `tests/test_base_declarada.py`, com quatro `policy_document` **commitados** (as contagens rodam em sessão própria, fora da transação do teste, então documento inserido via `db_session` seria invisível) e limpeza no teardown. **Só dois deles são alcançáveis pela busca**, e os outros dois são as duas maneiras reais de estar na base e fora do alcance: um sem vetor nenhum e um com vetor de outro modelo. É essa assimetria (4 vs 2) que torna os dois rodapés distinguíveis — com um corpus uniforme, usar a contagem errada passaria verde. A fixture ainda **asserta a pré-condição** de que a tabela está vazia antes de plantar: os números aqui são absolutos, e o dia em que outro módulo commitar um documento tem que sair como essa mensagem, não como um rodapé errado. Cada guarda foi verificada por mutação: o número vem do banco e não de um literal (apaga os documentos entre duas perguntas do mesmo `/ask` e o rodapé muda); o hit descartado pelo limiar não conta nem como cláusula nem como apólice; `NADA_RELEVANTE` usa a base pesquisável e **não** a do corpus; erro de query não declara base; worker sem declaração (chave ausente **ou** `tipo` desconhecido) não ganha rodapé; declaração malformada não vira 500; o rodapé sobrevive à queda do synthesizer; as outras três frases não declaram nada; contagem quebrada devolve a resposta inteira sem rodapé; e o prompt não menciona base.

**Exceção de worker não chega ao usuário, e a marca da falha é o `name` da mensagem.** Os dois workers rodam o corpo INTEIRO dentro de um `try` (não só o primeiro degrau) e, no `except`, chamam `_falha_de_worker(worker)`: um `logger.exception` com traceback + `request_id` + `client` (as mesmas chaves de `cost_event`, que é o que liga o incidente às linhas de custo e à pergunta), e uma `AIMessage` com `name="worker_error"` cujo conteúdo **não deriva da exceção**. Antes disso os workers devolviam `f"SQL error: {exc}"` / `f"RAG error: {exc}"` *como se fosse resultado*, e esse texto ia pro prompt do synthesizer — que podia parafraseá-lo — e, no caminho de degradação dele (`frase or resultado`), virava **literalmente** a resposta do `/ask`: um `OperationalError` do Postgres carrega host, porta, usuário e banco, e uma `AuthenticationError` da Voyage fala de chave de API. Detalhe de infraestrutura é informação do **operador**, e o canal do operador é o log. A marca é o `name` e não um prefixo no conteúdo porque prefixo é string mágica: um `startswith("SQL error")` que uma cláusula recuperada pode acionar por acidente e que se perde na primeira vez que alguém reescreve a frase — enquanto `name` é campo estruturado da própria `AIMessage`, o mesmo mecanismo que já distingue `sql_worker`/`rag_worker`/`final`. `WORKER_ERROR` fica **fora** de `WORKERS` de propósito: dentro, o texto da falha seria elegível como payload de síntese. Cobrir o nó inteiro (e não só o `get_schema`, como era) é o que impede que uma falha da Anthropic, uma resposta sem bloco `tool_use` ou um payload que não valida abortem o grafo e virem **500**. **A última porta do vazamento era o `run_query`, e ela fechou pela divisão `OperationalError` × `ProgrammingError`.** O `run_query` devolvia *qualquer* `psycopg.Error` como texto, então uma falha de conexão (banco reiniciado ou senha da role rotacionada **depois** do `get_schema` e antes do `run_query`) voltava como *resultado* do worker — e a mensagem de uma `OperationalError` de conexão é literalmente `connection to server at "host" (ip), port 5432 failed: password authentication failed for user "insurance_ro"`, que ia pro prompt do synthesizer e, no fallback dele, pra resposta do `/ask`. Agora `OperationalError` **sobe** e cai no `try` do `sql_worker` (→ `FALHA_INTERNA` + traceback), enquanto o resto continua voltando como texto. O argumento decisivo não é o vazamento, é a **simetria**: `get_schema()` nunca teve `except`, então o mesmo `OperationalError` era tratado de dois jeitos dependendo de qual das duas chamadas de banco o encontrasse. A divisão é a do próprio psycopg e cai exatamente onde precisa — tudo que o LLM consegue causar (`SyntaxError`, `UndefinedColumn`, `UndefinedTable`, `InsufficientPrivilege`) é `ProgrammingError`; `OperationalError` é banco inalcançável, conexão derrubada, shutdown, statement timeout, nenhum deles resposta a uma pergunta. "`run_query` nunca levanta" continua valendo pra **o que aquilo protegia** (SQL inválido do modelo não derruba o grafo); no servidor stdio a conexão morta virou erro de tool em vez de texto de resultado, o que é honesto. Fica um teste dos dois lados, porque só o de cima viraria exagero: um `UndefinedColumn` classificado como falha interna mandaria o operador procurar um incidente que não houve.

**O que NÃO está coberto: o supervisor.** Ele não tem `try` (a fatia foi explicitamente barrada de mexer nele), então uma falha da Anthropic, uma resposta sem bloco `tool_use` ou um payload que não valida na `SupervisorDecision` ainda abortam o `ainvoke` e saem como **500** — e ele é a primeira chamada paga e a mais exposta a uma indisponibilidade de API, ou seja, o 500 mais provável que sobrou. Fatia própria; é só aplicar o mesmo `_falha_de_worker` (o nome ficaria mentiroso — supervisor não é worker) ou envolver o `graph.ainvoke` no `/ask`.

**A leitura do synthesizer é do TURNO, não do histórico.** `resultados` e `falhou` são calculados sobre `state["messages"]` **depois da última `HumanMessage`** — a mesma pergunta que o nó já usa como `question`. Hoje é no-op (o `/ask` monta um State novo por request) e vira load-bearing quando o histórico atravessar turnos (WhatsApp): sem a fatia, uma falha do turno 1 faz o turno 2 responder `FALHA_INTERNA` sobre uma busca que rodou e não achou nada — e manda o operador procurar o traceback de **outro** request —, e um turno sem worker nenhum sintetiza a resposta do turno anterior com a confiança de quem acabou de consultar. Os dois casos têm teste, e o estado tem que ser o discriminante: com um resultado substantivo no turno atual, o `if not substantivos` já protege e a versão errada passa verde (aconteceu — o primeiro estado escrito não discriminava nada).

**`/ask` continua 200 numa falha de worker, e isso é escolha, não descuido.** A superfície do sistema é conversa (hoje `/ask`, amanhã WhatsApp): um 5xx entrega uma tela de erro do framework ou um balão vazio — o usuário fica sem resposta **e** sem saber se vale tentar de novo, enquanto "tive uma falha interna, tente em instantes" é informação acionável. O que o status resolveria (alarme, dashboard, investigação) é necessidade do **operador**, e o operador é servido pelo log, que carrega traceback + `request_id` + `client` — estritamente mais do que um 500 opaco carregaria. O comentário mora no docstring de `_final_answer` em `app/main.py`, que é onde alguém vai procurar "por que isso não é 500?".

**O synthesizer procura o resultado do worker MAIS RECENTE** (`m.name in WORKERS`, com `reversed` já entregando o último), não mais `m.name == "sql_worker"`. Com dois workers no grafo, fixar o SQL faria uma resposta de RAG ser sintetizada em cima de um SQL antigo do mesmo histórico — ou, sem SQL nenhum, cair no `NO_ANSWER` com as cláusulas certas na mensagem anterior.

**Nenhuma saída estática vale quando há resultado a apresentar, e entre elas a ordem vai da mais específica pra menos.** As quatro moram num bloco só, guardado por `if not substantivos` (`substantivos = [r for r in resultados if r != NADA_RELEVANTE]`): `FALHA_INTERNA` → `NADA_RELEVANTE` → `FORA_DE_ESCOPO` → `NO_ANSWER`. Cada degrau tem motivo. (1) **`FALHA_INTERNA` na frente de tudo**: se um worker caiu, "não achei no corpus" e "não trato desse assunto" são afirmações sobre o corpus e sobre o escopo que **ninguém verificou**, porque a consulta nem rodou — e `FORA_DE_ESCOPO` seria a pior, porque manda o usuário embora por causa de um banco fora do ar. (2) `NADA_RELEVANTE` só quando a busca de fato rodou (é o que `resultados` não-vazio significa naquele ponto). (3) `FORA_DE_ESCOPO` **depois** dos resultados, e não antes: com o grafo single-hop `next` e os resultados não podem se contradizer (o supervisor classifica antes de qualquer worker), então hoje isso é defesa em profundidade — e fica porque o multi-hop torna load-bearing de novo, já que um supervisor que decide depois de cada worker pode responder `unsupported` na segunda passada lendo justamente o "não encontrei" do `rag_worker`. (4) `NO_ANSWER` é o resto: ninguém trabalhou e nada quebrou. Pelo mesmo princípio, `NADA_RELEVANTE` e `FALHA_INTERNA` só são finais quando **não** há outro resultado — com um `sql_worker` tendo respondido antes, dizer "não encontrei nenhuma cláusula" (ou "falhei") jogaria fora o dado certo que está no histórico e já foi pago. Todos esses casos têm teste, e vários ficam verdes numa ordem errada — é a ordem das checagens que muda o resultado, não a existência delas, então os testes que os cobrem chamam o `synthesizer` **direto**, com o estado que o multi-hop reintroduz (via `/ask` são inalcançáveis hoje, e um teste roteado por lá passaria sem exercitar nada). `tests/test_graph_rag.py` roda **sem container** (busca falsa ⇒ a session nunca é usada, então `SessionLocal` é um objeto vazio de dois métodos) e cada teste guarda uma decisão que quebraria em silêncio: que o **texto** recuperado chega ao synthesizer (e não só que a busca rodou — um synthesizer que ignorasse o `rag_worker` devolveria a frase do fake do mesmo jeito); que `unsupported` gasta **uma** chamada de LLM no total, contada num contador global (`synth_calls == 0` sozinho não impediria um worker de ter rodado antes); que a resposta de busca vazia é `NADA_RELEVANTE` e é **diferente** de `FORA_DE_ESCOPO` e de `NO_ANSWER`; e, no fail-closed, tanto o valor devolvido por `route()` quanto o destino desse valor no mapa de arestas (`builder.branches[...].ends[END] == "synthesizer"`) — um `route` certo com o mapa errado mandaria o fail-closed pra lugar nenhum. As quatro decisões foram verificadas por mutação (cada uma deixa vermelho o teste que a guarda).

**O que `tests/test_falha_interna.py` prova, e por que a asserção principal é uma AUSÊNCIA.** Roda sem container (o `get_schema` é falso no caminho SQL; no RAG a busca falsa estoura antes de a session ser usada). As exceções plantadas carregam string de segredo plausível (host interno, porta, usuário do banco, chave de API), e o assert que importa é que **nada** dela aparece no corpo da resposta — palavra por palavra, não só a string inteira, senão uma versão que truncasse a mensagem da exceção continuaria vazando host e usuário. Cinco decisões estão travadas, cada uma verificada por mutação: (1) o **conteúdo** da mensagem de falha é estéril — testado chamando `_falha_de_worker` de dentro de um `except` de verdade, e é a **única** asserção que pega isso, porque o synthesizer curto-circuita pela marca do `name` e nem lê o conteúdo (uma versão que voltasse a interpolar `{exc}` passaria por todos os testes de ponta a ponta e só cobraria a conta no dia em que o histórico fosse logado, mandado pra um trace, ou reentrasse num prompt com o multi-hop); (2) o `try` cobre o **nó inteiro** — a exceção é plantada na chamada de LLM do worker, então mover o `except` de volta pra logo depois do `get_schema` deixa exatamente esse teste vermelho; (3) o log leva `exc_info` (`logger.exception`, não `logger.error`: sem traceback o operador sabe *que* caiu e não *por que*, o inverso do que a fatia trocou de lugar), `request_id` e `client`; (4) `synth_calls == 0` — não se paga pra reescrever uma frase pronta, e mandar exceção pro synthesizer é justamente como ela voltaria parafraseada; (5) o **caminho feliz continua feliz**, senão um `except` largo demais devolveria `FALHA_INTERNA` pra tudo e todos os testes de falha ficariam verdes.

**Alembic desligava os loggers do app dentro do pytest — `disable_existing_loggers=False` é o que trava isso.** O default do `logging.config.fileConfig` marca `disabled = True` em todo logger já criado no processo, e a migration roda **dentro** do processo do pytest (`command.upgrade` na fixture do container). O efeito era um falso verde silencioso: a partir do primeiro teste que sobe o banco, `logging.getLogger("app.agents.graph")` estava desligado, e qualquer teste posterior que asserisse sobre log via `caplog` não via registro nenhum — descoberto porque os testes de `FALHA_INTERNA` passavam sozinhos e falhavam na suíte completa. Em produção nunca machucou (o `alembic upgrade head` do Procfile roda em processo separado), mas aqui apagava exatamente a evidência que a suíte precisa ler — e o log é a única descrição do incidente, já que o usuário recebe frase genérica.

**Deductible terminology.** In residential CGs the term is **POS (Participação Obrigatória do Segurado)**, treated as a synonym for "franquia". The dominant pattern is "valor ou percentual definido na apólice" — the CG fixes the *structure*, the number lives in the customer policy. The validated `franquia_tipo` enum is `{sem_franquia, percentual, valor_fixo, definido_na_apolice}`. See `data/pilot_findings.md` for the reasoning behind every schema choice — read it before modeling tables.

**Three Postgres drivers, one URL normalizer.** The app runs on **asyncpg** (async), Alembic on **psycopg2** (sync), and the MCP SQL server on **psycopg3** (`psycopg`, sync — one fresh connection per call, no pool). `app/db_url.py::normalize_url(url, driver)` is the single point that rewrites any provider-supplied `DATABASE_URL` (`postgres://` vs `postgresql://`, and stripping libpq-only query params like `sslmode` that asyncpg rejects) into `postgresql+<driver>://`. The MCP server then strips `+psycopg` back off for the libpq conninfo.

**Cost attribution is built, and it covers the graph.** `app/cost.py` writes one `cost_event` row per LLM call. Money uses `Decimal`, never float; prices live in `app/pricing.json` (config, not code — Sonnet 5's promo pricing expires 2026-08-31) and the Batch API's 50% discount is applied via `BATCH_MULTIPLIER`. Unknown model → **fail loud** rather than record a wrong cost. The calls made *inside* the agent graph are attributed too: `record_call_cost()` opens its **own** session and commits immediately instead of riding the request's transaction — by the time it runs the call is already paid for, so the row must exist even if the request blows up afterwards. It stamps `cost_event.request_id` (a `uuid4` minted per `/ask`, which is what makes "what did this question cost?" answerable) and `cost_event.client` (the authenticated token's identity), both **nullable** because the offline extraction has neither — `NULL` means "call made outside a request", so there is no backfill. Those two values reach the node through **ContextVars** (`app/agents/context.py`), not through the graph `State`: the data is born at the HTTP edge but the writer is the node, and threading it through `State` would force every future node to carry fields that aren't part of the graph's domain. ContextVars are per-asyncio-task and child tasks inherit a copy, so concurrent `/ask`s can't see each other; `/ask` resets them in a `finally`. Two details in `app/agents/graph.py::_record_cost` are load-bearing: it records **`resp.model`, not the alias we sent** (`claude-haiku-4-5` resolves to `claude-haiku-4-5-20251001`, and the versioned id is the `pricing.json` key), and the whole write is **best effort** — a failure logs a warning and the request continues, because losing one row of observability is far cheaper than 500-ing an `/ask` that already cost money and already has an answer. It's called *before* the `tool_use` parse, since a malformed payload was billed too. `tests/test_cost_graph.py` proves the grain with a fake client (no test spends money): the happy path writes **three** rows — `supervisor → sql_worker → synthesizer` — because the grain is the *call*, not the agent. That count is also the regression test for the single-hop shape: with the old worker→supervisor edges it was four on a good run and up to ten on a bad one, and the `cost_event` rows are exactly what made that visible.

**SQL worker boundary + defense in depth.** `mcp_servers/postgres_mcp_server.py` is the SQL worker's window onto the data: a stdio FastMCP server exposing `get_schema()` and `run_query(sql)` scoped to the 5 domain tables. `get_schema`/`run_query` are plain module-level functions (the core logic) that are *both* registered as FastMCP tools (`mcp.tool()(fn)`) **and** imported directly by the in-process SQL worker — one implementation, two access paths. Writes are blocked twice: (1) a text filter in `run_query` (reject stacked statements → require a leading `SELECT` → reject any `FROM`/`JOIN` target outside the 5 domain tables → auto-append `LIMIT 100`), and (2) the physically read-only `insurance_ro` Postgres role (Alembic migration `4b285ffad59b`, `GRANT SELECT` only, password from `RO_ROLE_PASSWORD`) — so a write is impossible even if the text filter is bypassed. Connections prefer `DATABASE_URL_RO` (the RO role) when set, falling back to the admin `DATABASE_URL`. **`run_query` levanta em UM caso só, e é de propósito:** erro de query volta como texto (SQL inválido é resultado, e o caller não pode estourar por causa dele), mas `psycopg.OperationalError` de infraestrutura **sobe** — menos `_ERROS_DA_QUERY` (`statement_timeout` e os limites da classe 54), que são `OperationalError` causados pela própria query e continuam voltando como texto. Ver a seção da falha interna, abaixo, pro porquê. The folder is `mcp_servers/` (not `mcp/`) so it doesn't shadow the installed FastMCP `mcp` package; the filename uses an underscore (not a hyphen) so it's importable.

**Agent layer: supervisor de TRÊS rotas + SQL worker single-pass + RAG worker + synthesizer, async, served at `POST /ask`.** `app/agents/graph.py` is a LangGraph hub-and-spoke, **single-hop**: supervisor → worker → synthesizer, sem volta (ver a seção da R3b pro número que motivou). The **supervisor** is a real LLM call (`claude-haiku-4-5`) that classifies the question **once, before any work**, via forced structured output — `SupervisorDecision.next` is an enum (`Literal["sql_worker","rag_worker","unsupported","END"]`), the belt that stops the model routing to a worker that doesn't exist. `"END"` deixou de ser uma opção de roteamento (encerrar não é mais tarefa dele) mas **fica no enum como fail-safe**: fora dele, um modelo que devolvesse `END` quebraria a validação e derrubaria o request; dentro, cai no caminho do valor inválido e vira `NO_ANSWER`. O modelo **vê o enum** (ele está no `input_schema`), então o prompt tem uma linha mandando ignorá-lo — e ela diz só isso, **sem descrever o que o valor produz**: a versão que explicava ("faz o sistema devolver 'não consegui responder' sem nem tentar") anunciava, na última posição antes do fecho, uma saída de um token pra escapar de responder, competindo com a regra de desempate três linhas acima. Proibir não precisa do prêmio. O supervisor loga **WARNING** se vier `END` assim mesmo, **com `request_id` e `client`** — é a mesma chave de `cost_event.request_id`, e sem ela o aviso não se liga a request nenhum (dois `/ask` concorrentes e o operador vê um WARNING solto). O log é o que impede a fresta de ser silenciosa: de fora, esse `NO_ANSWER` é indistinguível de uma falha de infra, quando na verdade é uma pergunta respondível que ninguém tentou responder. `route()` fails closed (unknown `next` → `END`) and keeps the mechanical `MAX_ITERATIONS` circuit-breaker — **hoje inalcançável pelo caminho normal** (`route` roda uma vez só), mantido porque basta uma aresta de worker apontando de volta pro supervisor pra o ciclo voltar, e guarda que nunca dispara continua sendo guarda. The **SQL worker** is single-pass: question → `get_schema()` → LLM emits one `SELECT` (structured output `{"sql": ...}`) → `run_query()` through the RO role; **erro de QUERY volta como texto** (o LLM escreveu SQL inválido — isso é resultado, e o worker precisa poder contar isso ao synthesizer em vez de estourar), **erro de CONEXÃO sobe como exceção** e vira `FALHA_INTERNA` (ver a seção da falha interna abaixo). All Anthropic calls go through the `app/llm.py` factories (the one place to later add retry/timeout/cost tracking): `get_client()` (sync, used by the offline extraction) and `get_async_client()` (used by the graph nodes). Importing the module no longer runs the graph — the demo `ainvoke` is behind `if __name__ == "__main__"` (`python -m app.agents.graph`). O **RAG worker** entrou na R3b (seção acima). *Not yet:* a ReAct refinement loop in the SQL worker, e um worker de `extraction`.

**The synthesizer is always the last node.** `synthesizer` turns the worker's raw output (`SQL: … / Result: [(7,)]`, ou as cláusulas do `rag_worker`) into one pt-BR sentence, so `/ask` returns prose instead of a tuple dump. Wiring: the supervisor's conditional edge maps `END → "synthesizer"`, os dois workers têm aresta direta pro synthesizer, e o synthesizer edges to `END` — quando o synthesizer entrou, **`route()` não mudou**: ele continuava devolvendo `END`, só o destino desse valor no `path_map` é que mudou. (A R3b mexeu no `route()`, mas pelo outro motivo: o `rag_worker` é um destino novo — ver a seção da R3b.) Three decisions carry weight. (1) **No worker result → static sentence, no LLM call**: on the unsupported-question path (and on a circuit breaker that cut before any query) there is nothing to synthesize, and paying a call to write "I don't know" is burning money; that's why `NO_ANSWER` now lives in `graph.py` rather than `app/main.py` — the graph writes the answer, the API only reads it. A R3b estendeu essa mesma regra pras outras duas frases estáticas (`FORA_DE_ESCOPO`, `NADA_RELEVANTE`), e a fatia da falha interna pra quarta (`FALHA_INTERNA`). (2) **Free text, not structured output** — unlike every other node, the payload is one prose sentence, and forcing a tool would only wrap a string in JSON. This is also what the test fakes dispatch on: *no `tools` in the call ⇒ it's the synthesizer*. (3) **A failed synthesis degrades to the worker's raw text** (`frase or resultado`, covering both the exception and an empty response) instead of raising in the last node — ugly to read, but it is a real, already-paid answer, and 500-ing an `/ask` that already has the data is strictly worse. Cost is recorded through the same best-effort `_record_cost` with `agent_name="synthesizer"`. `tests/test_synth.py` pins all four behaviours; the load-bearing assertion is `synth_calls == 0` on the fallback path, which is what proves the "don't pay to say I don't know" rule.

**The graph nodes are async; the SQL access is not.** `supervisor`, `sql_worker` and `synthesizer` are `async def` so they don't block FastAPI's event loop on LLM calls. `get_schema()`/`run_query()` stay **psycopg3 sync** (one fresh connection per call, no pool) and are called through `asyncio.to_thread(...)` — deliberately: swapping the MCP server to an async driver would fork the one implementation the stdio server and the in-process worker share. `route()` stays sync — it only reads `State`, no I/O.

**`POST /ask` (`app/main.py`).** `{question: str (3..500)}` → `{answer, iterations}`, invoking `graph.ainvoke`. `_final_answer()` reads `state["messages"][-1]` and returns it when it's the `AIMessage` named `final` — since the synthesizer closes every exit path, the answer *is* the last message and there is nothing to scan for. The `NO_ANSWER` check on that message is only a belt: if the history ever ends with something else, we return the fallback rather than handing an agent's internal reasoning to the caller as an answer. `tests/test_ask.py` exercises the whole graph with a fake async client (dispatching on the forced tool name) plus fake `get_schema`/`run_query`, so **no test spends money**; the load-bearing case is now the **chamada única**: um supervisor teimoso (o fake que só sabe dizer `sql_worker`) tem que produzir `iterations == 1` e uma chamada só — antes esse mesmo fake media o circuit breaker em `MAX_ITERATIONS` passadas, e o que a medição mostrou é que aquele era o caso *normal*, não o patológico. O circuit breaker ganhou teste próprio, forjando `iterations` direto no State.

**Auth + rate limit on `/ask` (`app/auth.py`, `app/limits.py`).** `/ask` is the only paid endpoint, so it's closed; `/health` and `/health/db` stay **open** (Railway's healthcheck sends no `Authorization`). `API_TOKENS` is `"nome:token,nome2:token2"` — tokens carry an **identity**, not one shared secret, which is what makes per-client limits and single-client revocation possible. `_load_tokens()` reads the env **inside the function** (importing `app.main` must not require env vars, and tokens can rotate without a rebuild). Fail-closed on config: missing/empty `API_TOKENS` → **500**, not 401 — a 401 would disguise a broken deploy as a bad client credential. Token comparison uses `secrets.compare_digest` over **all** tokens with **no `break`** (`==` leaks the correct prefix by timing; a `break` would leak the position in the list), and compares **bytes** — `compare_digest` on `str` raises `TypeError` on non-ASCII, and the credential comes from a client-controlled header, so a token with an accent would 500 instead of 401. The token is never logged, not even on failure. Two slowapi limits apply, **at different layers, and the split is load-bearing**. The per-IP ceiling (`ASK_RATE_LIMIT_IP`, default `10/minute`) is a `default_limits` enforced by `SlowAPIMiddleware`, which runs before routing and dependencies — so it also counts requests that die at the **401**. It covers every non-exempt route but is **counted per path** (slowapi's `key_style` defaults to `"url"`, so the bucket key is `(IP, path)`) — `10/minute` is per route, not across the API. As a route decorator it was never reached (`require_client` is a dependency, and FastAPI resolves dependencies before invoking the endpoint), which let anyone hammer `/ask` with invalid tokens for free. The per-client quota (`ASK_RATE_LIMIT_CLIENT`, default `30/hour`) stays a **route decorator** because it keys on `request.state.client_name`, which only exists after auth. The Limiter's global `key_func` is therefore `get_remote_address` (`default_limits` inherits it) and `client_key` is passed explicitly on the decorator. **No double counting** — verified in slowapi 0.1.10's `_check_request_limit`: the default limits are folded into the route check only when `combined_defaults` is true, i.e. when every route limit has `override_defaults=False`, and `.limit()` defaults it to `True`; so the middleware pass evaluates only the IP ceiling and the decorator pass only the client quota. **Landmine:** `_should_exempt` skips the middleware entirely for any route present in `_route_limits`, and only *static* limits land there (callables go to `_dynamic_route_limits`) — turning `ask_client_limit` into a plain string would silently stop the IP ceiling from covering `/ask`'s 401s; `test_teto_por_ip_cobre_request_sem_auth` is the guard. `/health` and `/health/db` are `@limiter.exempt` (inside `@app.get`, so the registered route is the marked function): Railway polls them in a loop, and quota burned there would return 429 to the platform, which then tears down a healthy service. Both limits are read from env through **callables**, so they're re-evaluated per request and the tests can tighten them; `_limit_from_env` validates with `limits.parse_many` and falls back to the default, because slowapi **fails open** on an unparseable limit (logs and applies none), so a typo in the Railway env would silently switch off the spend ceiling. `require_client` writes `request.state.client_name` **itself** — the decorator's wrapper builds its key at endpoint-call time, so an assignment in the route body would land too late. Deploying behind a proxy needs `uvicorn --proxy-headers --forwarded-allow-ips=<proxy>`, otherwise every request carries the proxy's IP and the per-IP ceiling treats all callers as one.

**Intended (not built):** the extraction worker, a ReAct loop in the SQL worker, and a HMAC-verified WhatsApp (Meta Cloud API) surface.

## SUSEP corpus pipeline (`scripts/`)

The harvester builds the corpus from three login-free public SUSEP endpoints. Critical gotchas baked into `susep_harvest.py`:
- The Olinda OData index (`DadosProdutos`) **only accepts `$format=json`** — any `$top`/`$filter`/`$select` returns HTTP 500, so the full dataset is fetched and cached locally.
- The version-resolution endpoint enforces a **~14-query-per-session quota**, after which it returns HTTP 200 with an *empty page* (not 429). The harvester detects this and rotates the session cookie to reset the quota, keeping ~1 req/s.

```bash
python scripts/susep_harvest.py                # in-force version per process
python scripts/susep_harvest.py --all-versions # full version history
python scripts/susep_harvest.py --limit 5      # smoke test
```

**Script defaults are anchored to the repo root** via `Path(__file__).resolve().parent.parent`, so they read/write `data/corpus/` correctly regardless of CWD (run them from anywhere; override with `--out`/`--index-cache`).

**The PDFs are gitignored** (`data/corpus/*.pdf`) — large and public. Only `corpus_manifest.json` is committed; it records per-version provenance (process, internal id, insurer, CNPJ, url, sha256, dates, `has_text`) and lets anyone re-download and verify the corpus by hash. The download endpoint keys on an **internal numeric id**, while the index keys on **process number** (`15414.NNNNNN/AAAA-DD`) — bridging the two is what the resolve step does.

The extraction logic lives in **`app/extraction/`** (importable modules: `pdf` → `extract` → `schema` → `persist`, plus `manifest`, `batch`, `sample`, `evaluate`); the `scripts/` files are thin CLI wrappers over it. The split is deliberate — persistence can be re-run without paying for the LLM again:
- `scripts/run_extraction.py <pdf> --out <json>` — pdfplumber → Anthropic forced tool-use (single tool, `input_schema` = the Pydantic tree, `tool_choice` forced) → validated **nested** output, cross-checked against the manifest. Needs `ANTHROPIC_API_KEY`.
- `scripts/persist_extraction.py <json> --pdf <pdf>` — deterministic flatten of the nested tree into the 5 tables; the LLM returns a tree because it doesn't know DB ids, and this layer assigns ids/FKs. Provenance comes from the manifest, not the LLM read. Needs `DATABASE_URL`.
- `scripts/run_batch.py` / `app/extraction/batch.py` — mass extraction via the **Batch API at 50% price** (offline, nobody waiting); `sample.py` picks the corpus sample; `evaluate.py` scores a cheaper model against a hand-checked golden (`data/golden/`). `rescue_batch.py` re-reads an already-paid batch's results (they persist ~29 days) so a local *parse* failure costs nothing to retry.

The extracted JSON under `data/extractions/` is gitignored derived output, like the PDFs.

The other scripts are one-off, not production: `susep_probe.py` (blind-sampling viability probe that established corpus volume) and `pilot_extraction.py` (manual hand-read extraction of 2 CGs that validated the schema — produces `data/pilot_extraction.json`, summarized in `data/pilot_findings.md`).
