# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-agent system that turns Brazilian home-insurance *condições gerais* (general terms registered with SUSEP) into a queryable knowledge base. It answers **coverage-structure** questions ("which insurers cover windstorm without a deductible?"), not pricing — the corpus describes products, and prices live in individual customer policies which are out of scope.

The project is mid-build. What exists: the data pipeline (harvester + validated extraction schema + `app/extraction/` LLM pipeline), a FastAPI/Postgres skeleton, the ORM models + Alembic migrations (`app/models.py`), per-call cost attribution (`app/cost.py` + `pricing.json`) wired into the agent graph, a standalone Postgres MCP SQL server (`mcp_servers/`), a first real agent graph (`app/agents/graph.py`: LLM supervisor + single-pass SQL worker + synthesizer — see below) served at `POST /ask` (protected by Bearer auth + rate limiting — `app/auth.py`, `app/limits.py`), a testcontainers-backed test suite, and the RAG worker's **vector infrastructure** (pgvector + `clause_chunk` — R1, storage only). What does *not* exist yet: the extraction/RAG workers themselves (nothing chunks, embeds or retrieves yet — that's R2/R3), a ReAct refinement loop in the SQL worker, and the WhatsApp surface. See the Roadmap in `README.md` for current state before assuming a component exists.

## Architecture & key decisions

**Async-only data layer.** `app/db.py` uses SQLAlchemy 2.0 async (`asyncpg` driver). The `DATABASE_URL` **must** use the `postgresql+asyncpg://` scheme, not plain `postgresql://`. The async route (`/health/db`) injects a session via FastAPI `Depends(get_session)`.

**A engine é preguiçosa: `DATABASE_URL` é lida em runtime, não no import.** `app/db.py` não constrói mais nada no nível do módulo. `_sessionmaker()`, cacheado com `@lru_cache(maxsize=1)`, lê o env, normaliza a URL e cria a engine + o `async_sessionmaker` **na primeira chamada**; `SessionLocal()` é uma função que delega pra ele. O motivo: com `os.environ["DATABASE_URL"]` no topo do módulo, qualquer `import app.main` num ambiente sem banco configurado morria com `KeyError` **no import** — inclusive durante a *coleta* do pytest, antes do testcontainers ter subido o Postgres. Esse bug voltou 4×, sempre disfarçado de "ordem de fixture", e é o que impedia um CI sem `.env`. Três detalhes carregam peso. (1) O `lru_cache` **é** a engine única do processo: sem ele, cada `SessionLocal()` criaria uma engine (e um pool) nova e vazaria conexões — não construa engine por chamada, só via o cache. (2) `SessionLocal` continua sendo um **atributo chamável do módulo** de propósito: 6 scripts fazem `from app.db import SessionLocal` e `tests/test_cost_graph.py`/`tests/test_synth.py` trocam esse atributo com `monkeypatch.setattr("app.db.SessionLocal", ...)` — renomear quebra os dois lados. É também por isso que o import de `app.db` dentro de `record_call_cost` continua sendo local: o motivo original (importar `app.db` exigia env) caiu, mas o import tardio é o que resolve `SessionLocal` no momento da chamada e faz o monkeypatch pegar. (3) `load_dotenv()` fica **no topo**: em dev local o `.env` continua sendo a fonte da URL, e em CI, sem arquivo, é no-op — ele não exige nem lê a variável. `tests/test_lazy_db.py` é a trava: roda `import app.main` (e cada degrau da cadeia: `app.db`, `app.cost`, `app.agents.graph`) num **subprocesso** com env limpo, cwd fora do repo e `load_dotenv` neutralizado, porque dentro do processo do pytest o env já está populado pela fixture do container e não se prova nada. Ele também **chama `SessionLocal()` pra valer** e roda um `SELECT 1` no que voltou: nenhum outro teste faz isso (os de custo trocam o atributo por monkeypatch, e a fixture `client` sobrescreve `get_session`), então sem esse assert um bug *dentro* de `SessionLocal` passaria pela suíte inteira verde — verificado plantando o bug.

**As gambiarras de ordem de fixture da F3/F4 agora são redundantes.** `ask_client` em `tests/test_cost_graph.py` e `tests/test_synth.py` pede `db_url`/`cost_rows` antes só pra garantir que o container (e portanto `DATABASE_URL`) existisse antes de `import app.main` — com a engine preguiçosa isso não é mais necessário, e os docstrings dessas fixtures descrevem um problema que não existe mais. **Foram mantidas de propósito** na fatia da correção (remover é ruído separado, e `cost_rows` continua obrigatória nos testes que de fato contam linhas em `cost_event`); quem mexer nesses arquivos depois pode simplificar a assinatura sem medo.

**CI (`.github/workflows/ci.yml`).** `pull_request` + push na `main`; ubuntu-latest, Python 3.11, `pip install -r requirements.txt`, `pytest -q`. O job **não** seta `DATABASE_URL` nem cria `.env`, e isso é o ponto: quem sobe o Postgres é o testcontainers dentro da própria suíte (o runner já traz Docker; `TESTCONTAINERS_RYUK_DISABLED` vem do `conftest.py`). Ou seja, o CI só é verde por causa da engine preguiçosa — ele é a prova viva da correção, não só um gate. Também não precisa de secrets: nenhum teste gasta dinheiro (todos usam fakes), então `ANTHROPIC_API_KEY` não entra.

**Port 5433.** docker-compose maps Postgres to host `5433` (not the default 5432) to avoid colliding with a local Postgres; `.env.example` reflects this.

**The corpus is general terms, not policies.** This is the central scoping decision and it shapes the schema: a document describes a *product*. The extraction grain is therefore **(insurer × coverage)**, and coverages are normalized **by peril, not by commercial name**, because insurers bundle perils differently. That makes `coverage ↔ peril` many-to-many. The tables are built in `app/models.py`: `policy_document`, `coverage` (includes a nullable `plan` free-text commercial tier), `peril`, `coverage_peril` (join), `exclusion` (scope = general or per-coverage). Categorical columns feed the future SQL worker; raw-text columns feed the future RAG worker.

**Infra de vetores (R1 do worker RAG): `clause_chunk` + pgvector.** Esta fatia é **só armazenamento** — nada faz chunking, embedding ou retrieval ainda (R2/R3), e não existe nó novo no grafo. A imagem do Postgres virou `pgvector/pgvector:pg16` **nos dois lugares** (`docker-compose.yml` e o `PostgresContainer` do `tests/conftest.py`): é a mesma `postgres:16` com a extensão compilada, e se as duas divergirem o `CREATE EXTENSION vector` da migration quebra justamente onde ninguém olha (CI). A tabela é **separada de propósito**: o texto já existe em `exclusion.clause_text` e `coverage.deductible_rule_text`, mas lá o grão é a *linha extraída* e aqui é o **chunk** — uma cláusula longa vira vários pedaços, cada um com o seu vetor; guardar o embedding na tabela de origem forçaria um chunk por linha e amarraria o schema de domínio ao modelo de embedding da vez. A origem do chunk é um **arco exclusivo** — `exclusion_id` **ou** `coverage_id`, exatamente um, imposto pelo check `ck_clause_chunk_exactly_one_source` — e os uniques `(exclusion_id, chunk_index)` / `(coverage_id, chunk_index)` são o que torna a re-indexação idempotente. O modelo é **voyage-4-lite / `EMBEDDING_DIM = 1024`** (multilíngue, e o corpus é pt-BR; barato; dimensão menor deixa o índice HNSW leve); a dimensão fica **no tipo da coluna** porque o Postgres precisa dela pra indexar, então trocar de modelo é migration, não config. `embedding` e `embedding_model` são nullable porque chunking e embedding são passos separados: a linha nasce com o texto e recebe o vetor depois — `NULL` = "ainda não indexado".

**A migration do `clause_chunk` (`d3f8a1c60b47`) é escrita à mão, e o índice mora nos dois lados.** O autogenerate enxerga a tabela e a coluna `vector(1024)`, mas não emite nem o `CREATE EXTENSION` (sem ele o `CREATE TABLE` falha com *"type vector does not exist"*) nem o índice HNSW (Alembic não modela operator class), então a ordem extensão → tabela → índice é escrita na mão. O `downgrade()` desfaz índice → tabela e **não dropa a extensão**: ela é do banco, não desta tabela. O índice é criado com SQL cru na migration **mas também declarado no `__table_args__`** do modelo (`Index(..., postgresql_using="hnsw", postgresql_ops={"embedding": "vector_cosine_ops"})`) — sem essa declaração o próximo `alembic revision --autogenerate` vê um índice que o modelo não conhece e emite um `drop_index`, derrubando o índice de vetor de brinde numa migration sobre outro assunto. `alembic check` é o que trava isso (verificado: com o índice só na migration, ele acusa `remove_index`).

**O arco exclusivo (`a4c91e5d7f28`) substituiu o ponteiro polimórfico da R1.** O desenho original era `source` (texto) + `source_id` (id **sem FK**), e tinha dois furos que o code review pegou. (1) `source_id` não era chave estrangeira: apagar a exclusão de origem deixava o chunk apontando pro vazio e — como a re-extração reusa ids — o chunk passava a citar uma cláusula *diferente*, destruindo exatamente a garantia de "citar a origem" que a coluna existia pra dar. (2) O `UniqueConstraint(source, source_id, chunk_index)` **não** impunha idempotência: `source_id` era nullable e o Postgres trata `NULL`s como distintos num índice único, então duas linhas idênticas entravam as duas (verificado empiricamente). Agora são duas FKs de verdade (`exclusion_id`, `coverage_id`) com um check XOR (`(exclusion_id IS NOT NULL) <> (coverage_id IS NOT NULL)`); `coverage_id` **mudou de significado** — era cópia denormalizada da cobertura dona da exclusão (que podia divergir de `exclusion.coverage_id`), agora é o braço "este chunk é a regra de franquia desta cobertura". A migration é escrita à mão e faz `DROP COLUMN`, o que só é seguro porque `clause_chunk` está **vazia em todo ambiente** (a R1 entregou só armazenamento) — não há backfill. Ela também cria `ix_clause_chunk_document_id`: o Postgres não indexa coluna filha de FK sozinho, e sem isso todo `DELETE` em `policy_document` viraria seq scan na maior tabela do schema (`exclusion_id`/`coverage_id` já saem indexadas pelos dois índices de idempotência).

**As FKs do arco são compostas com `document_id`, e é isso que fecha o buraco de verdade.** Com FK simples (`exclusion_id → exclusion.id`) sobrava um terceiro caso ruim, além dos dois de cima: nada obrigava `document_id` a ser o documento da origem, então um chunk com `document_id` do documento B e `exclusion_id` de uma exclusão do documento A entrava sem reclamar (verificado empiricamente — passava). E aí o buraco reabria pela porta lateral: `delete_document_by_hash(A)` apaga chunks **por `document_id`**, não veria esse chunk, e estouraria `ForeignKeyViolation` ao apagar a `exclusion` — o documento pela metade que esta fatia inteira existe pra impedir. As FKs são `(document_id, exclusion_id) → exclusion(document_id, id)` e `(document_id, coverage_id) → coverage(document_id, id)`; o Postgres exige unique/PK no lado referenciado, daí os `UniqueConstraint("document_id", "id")` em `coverage` e `exclusion` — redundantes como unicidade (`id` já é PK), presentes **só** como alvo da FK. O que faz isso conviver com o arco é o **MATCH SIMPLE** (o padrão): se qualquer coluna da FK é `NULL` a constraint não é checada, então o braço não usado fica inerte e só o preenchido é validado. É também o que torna verdadeiro o comentário em `persist.py` de que um `DELETE` por `document_id` cobre os dois braços — antes isso era presunção, agora é garantia do schema.

**Os dois índices de idempotência são únicos parciais, não `UNIQUE` constraints.** Por desenho metade das linhas tem `exclusion_id` `NULL` e a outra metade `coverage_id` `NULL`, então um índice total carregaria uma entrada morta por linha do outro braço — o dobro do tamanho, na tabela que também carrega o HNSW. O predicado (`WHERE exclusion_id IS NOT NULL`) não afrouxa nada: as linhas que ele exclui são exatamente as que o `NULL` já tornava não-conflitantes. Continuam servindo a validação da FK, porque `exclusion_id = $1` implica o predicado. Os nomes seguem `uq_...`, então as mensagens de erro (e os `pytest.raises(match=...)`) não mudaram.

**O `REVOKE`/`GRANT` é guardado por um `DO` block em `pg_roles`.** Role é objeto de **cluster**, não de banco, e a cadeia de migrations só garante objetos do banco: um `pg_dump` restaurado num cluster novo (`pg_dump` não emite roles) chega aqui sem `insurance_ro` e a migration morre com `role "insurance_ro" does not exist` — no Procfile, que roda `alembic upgrade head` no boot, isso é o web process que não sobe. O Postgres não tem `REVOKE ... IF EXISTS` pra role, então o guard é explícito (`_if_role_exists()`). Verificado: dropando a role antes do upgrade, a migration passa.

**O `downgrade()` esvazia `clause_chunk` antes de reconstruir o desenho antigo.** `source` volta como `NOT NULL` e `exclusion_id` some — não há como reconstruir o ponteiro antigo a partir do arco sem inventar dado. Sem o `DELETE`, o downgrade numa base já indexada (o mundo pós-R2) dropava `exclusion_id` e só então estourava em `ADD COLUMN source NOT NULL` com *"column contains null values"*. Descartar chunk é recuperável — texto e embedding saem de re-indexar cláusulas que continuam em `exclusion.clause_text` / `coverage.deductible_rule_text`; morrer no meio do downgrade não é. Enquanto a R2 não existir a tabela está vazia e o `DELETE` é no-op.

**`delete_document_by_hash` apaga `clause_chunk` primeiro.** A ordem é `clause_chunk → coverage_peril → exclusion → coverage → policy_document`: o chunk é o filho mais fundo, referenciando as três tabelas acima dele. Sem isso o DELETE estoura com `ForeignKeyViolation` já em `exclusion` e deixa o documento **pela metade** — o fluxo `--force` de re-extração quebraria assim que a R2 começasse a gravar chunks. `tests/test_delete.py::test_delete_removes_clause_chunks` é a trava, e cobre os **dois** braços do arco (um chunk por exclusão, um por cobertura); foi escrito antes da correção e confirmado vermelho com a FK violation.

**`clause_chunk` fica fora do alcance do worker SQL — em duas camadas independentes.** A tabela está fora do `TABLES` do MCP server (o worker responde por agregação sobre colunas categóricas; expor uma coluna vetorial no `get_schema()` só gastaria contexto), mas isso sozinho não protegia nada: o filtro textual do `run_query` só olha o primeiro token, então um `SELECT * FROM clause_chunk` escrito pelo LLM passaria, e o `LIMIT 100` automático despejaria 100 vetores de 1024 floats (~1 MB de texto) no contexto da chamada seguinte, num projeto que mede custo por chamada.

As duas camadas são: (1) **allowlist de tabela no `run_query`** — `_tabelas_fora_da_allowlist()` extrai os alvos de `FROM`/`JOIN` e rejeita o que não for tabela de domínio nem CTE local; (2) **`REVOKE SELECT ON clause_chunk FROM insurance_ro`** na migration `a4c91e5d7f28`, **cirúrgico** (o `ALTER DEFAULT PRIVILEGES` da `4b285ffad59b` continua valendo pras tabelas futuras, e as tabelas de domínio seguem legíveis). **Nenhuma cobre o caso da outra**, e é por isso que existem as duas: o REVOKE não participa de nada quando `DATABASE_URL_RO` não está configurada e o `_conninfo()` cai silenciosamente pro `DATABASE_URL` admin (o caso do CI, e de qualquer deploy que só setou a URL admin); a allowlist não seguraria uma role com permissão de escrita se o filtro de `SELECT` fosse burlado. A allowlist não é um parser de SQL e não precisa ser — subquery e CTE também usam `FROM`, então toda leitura de tabela passa por lá; `FROM (SELECT ...)` não casa de propósito (o que importa está dentro), e nomes de CTE são coletados à parte pra não virarem falso positivo.

Os testes cobrem os dois lados de cada camada. `test_worker_sql_nao_enxerga_clause_chunk` assere `has_table_privilege` falso pra `clause_chunk` **e verdadeiro pra `exclusion`**, senão um revoke largo demais passaria despercebido derrubando o worker inteiro — mas ele afirma o privilégio da *role*, não que alguém conecte com ela, e é justamente esse limite que a allowlist cobre. `tests/test_sql_allowlist.py` roda **sem banco** (a rejeição acontece antes do `_connect()`) e também tem os dois lados: as tabelas proibidas rejeitadas, e as queries legítimas do domínio — join, alias, CTE, subquery — aprovadas, senão um `return "Error"` incondicional passaria no teste de rejeição e derrubaria o worker em silêncio. O `mcp_servers/test_readonly_role.py` (standalone, não pytest) ganhou uma quarta checagem: `SELECT` em `clause_chunk` esperando `InsufficientPrivilege` — é o único lugar que exercita o REVOKE por uma conexão libpq real autenticada **como** a role, que é o caminho que o worker usa de verdade.

**O que `tests/test_vector.py` prova.** Extensão instalada, round-trip de 1024 floats, ordenação por distância, índice HNSW com a operator class certa, os dois braços ruins do arco, idempotência da re-indexação, o revoke, e dimensão errada rejeitada. Cinco são load-bearing.

Os dois primeiros cobrem a **FK em si**, que é a manchete da correção e mesmo assim não tinha teste nenhum: `test_fk_rejeita_origem_inexistente` (ponteiro órfão) e `test_fk_impede_apagar_a_exclusao_citada` (o dano real do id sem FK não é o `NULL`, é a re-extração reciclar o id e o chunk passar a citar outra cláusula em silêncio). Sem eles a FK inteira podia sumir da migration com a suíte verde — o check XOR continua disparando, os uniques continuam disparando, e o teste de delete passa porque apaga os chunks primeiro de qualquer jeito. `test_fk_composta_rejeita_chunk_de_outro_documento` é o terceiro: prova que `document_id` e a origem do arco têm que concordar, o caso que passava antes da FK composta. O de **distância**: `cosine_distance` vira o operador `<=>`, que num `float[]` comum nem existiria — é ele que prova que o tipo é vetor de verdade; insere os chunks na ordem **inversa** da esperada e consulta nos dois sentidos, porque com a ordem "certa" de inserção o teste passaria mesmo se o `ORDER BY` fosse ignorado. O do **índice**: sem ele, apagar o `CREATE INDEX ... USING hnsw` da migration (ou trocar `vector_cosine_ops` por `vector_l2_ops`) deixaria todo o resto verde — com duas linhas o planner ordena por seq scan de qualquer jeito, e uma opclass errada simplesmente nunca seria usada. O de **dimensão** casa a mensagem `expected 1024 dimensions` em vez de aceitar qualquer `DBAPIError`, que seria satisfeito por uma FK ou um NOT NULL vizinhos sem nunca exercitar a dimensão. Os dois testes de índice checam a **definição** (`(document_id)`, `WHERE (... IS NOT NULL)`), não só a existência da linha em `pg_indexes`: com um `assert indexdef is not None` bastava criar o índice na coluna errada pro teste passar verde com o seq scan intacto — o nome do índice não prova o conteúdo dele. Os testes que esperam falha rodam dentro de `begin_nested()` (savepoint): o INSERT abortado aborta a transação junto, e sem o savepoint derrubaria a transação da fixture que mantém os testes isolados.

**`pgvector` é pinado (`==0.5.0`), como todo runtime dep.** O range aberto `>=0.3.6` atravessava uma mudança de comportamento: em 0.3.x o `Vector` valida a dimensão **no cliente** e levanta `StatementError` (nada chega ao servidor), então o teste de dimensão falharia no piso do próprio range declarado — e o 0.3.x devolve `np.ndarray` na leitura, contradizendo a anotação `Mapped[list[float] | None]`.

**Deductible terminology.** In residential CGs the term is **POS (Participação Obrigatória do Segurado)**, treated as a synonym for "franquia". The dominant pattern is "valor ou percentual definido na apólice" — the CG fixes the *structure*, the number lives in the customer policy. The validated `franquia_tipo` enum is `{sem_franquia, percentual, valor_fixo, definido_na_apolice}`. See `data/pilot_findings.md` for the reasoning behind every schema choice — read it before modeling tables.

**Three Postgres drivers, one URL normalizer.** The app runs on **asyncpg** (async), Alembic on **psycopg2** (sync), and the MCP SQL server on **psycopg3** (`psycopg`, sync — one fresh connection per call, no pool). `app/db_url.py::normalize_url(url, driver)` is the single point that rewrites any provider-supplied `DATABASE_URL` (`postgres://` vs `postgresql://`, and stripping libpq-only query params like `sslmode` that asyncpg rejects) into `postgresql+<driver>://`. The MCP server then strips `+psycopg` back off for the libpq conninfo.

**Cost attribution is built, and it covers the graph.** `app/cost.py` writes one `cost_event` row per LLM call. Money uses `Decimal`, never float; prices live in `app/pricing.json` (config, not code — Sonnet 5's promo pricing expires 2026-08-31) and the Batch API's 50% discount is applied via `BATCH_MULTIPLIER`. Unknown model → **fail loud** rather than record a wrong cost. The calls made *inside* the agent graph are attributed too: `record_call_cost()` opens its **own** session and commits immediately instead of riding the request's transaction — by the time it runs the call is already paid for, so the row must exist even if the request blows up afterwards. It stamps `cost_event.request_id` (a `uuid4` minted per `/ask`, which is what makes "what did this question cost?" answerable) and `cost_event.client` (the authenticated token's identity), both **nullable** because the offline extraction has neither — `NULL` means "call made outside a request", so there is no backfill. Those two values reach the node through **ContextVars** (`app/agents/context.py`), not through the graph `State`: the data is born at the HTTP edge but the writer is the node, and threading it through `State` would force every future node to carry fields that aren't part of the graph's domain. ContextVars are per-asyncio-task and child tasks inherit a copy, so concurrent `/ask`s can't see each other; `/ask` resets them in a `finally`. Two details in `app/agents/graph.py::_record_cost` are load-bearing: it records **`resp.model`, not the alias we sent** (`claude-haiku-4-5` resolves to `claude-haiku-4-5-20251001`, and the versioned id is the `pricing.json` key), and the whole write is **best effort** — a failure logs a warning and the request continues, because losing one row of observability is far cheaper than 500-ing an `/ask` that already cost money and already has an answer. It's called *before* the `tool_use` parse, since a malformed payload was billed too. `tests/test_cost_graph.py` proves the grain with a fake client (no test spends money): the happy path writes **four** rows, not two — `supervisor → sql_worker → supervisor → synthesizer`, because the supervisor runs again to decide the `END`, the synthesizer then writes the answer, and the grain is the *call*, not the agent.

**SQL worker boundary + defense in depth.** `mcp_servers/postgres_mcp_server.py` is the SQL worker's window onto the data: a stdio FastMCP server exposing `get_schema()` and `run_query(sql)` scoped to the 5 domain tables. `get_schema`/`run_query` are plain module-level functions (the core logic) that are *both* registered as FastMCP tools (`mcp.tool()(fn)`) **and** imported directly by the in-process SQL worker — one implementation, two access paths. Writes are blocked twice: (1) a text filter in `run_query` (reject stacked statements → require a leading `SELECT` → reject any `FROM`/`JOIN` target outside the 5 domain tables → auto-append `LIMIT 100`), and (2) the physically read-only `insurance_ro` Postgres role (Alembic migration `4b285ffad59b`, `GRANT SELECT` only, password from `RO_ROLE_PASSWORD`) — so a write is impossible even if the text filter is bypassed. Connections prefer `DATABASE_URL_RO` (the RO role) when set, falling back to the admin `DATABASE_URL`. `run_query` never raises: SQL *and* connection errors come back as text so the caller doesn't crash. The folder is `mcp_servers/` (not `mcp/`) so it doesn't shadow the installed FastMCP `mcp` package; the filename uses an underscore (not a hyphen) so it's importable.

**Agent layer: real supervisor + single-pass SQL worker + synthesizer, async, served at `POST /ask`.** `app/agents/graph.py` is a LangGraph hub-and-spoke. The **supervisor** is a real LLM call (`claude-haiku-4-5`) that decides the next hop via forced structured output — `SupervisorDecision.next` is an enum (`Literal["sql_worker","END"]`), the belt that stops the model routing to a worker that doesn't exist. `route()` fails closed (unknown `next` → `END`) and keeps a mechanical iteration circuit-breaker (`MAX_ITERATIONS`). The **SQL worker** is single-pass: question → `get_schema()` → LLM emits one `SELECT` (structured output `{"sql": ...}`) → `run_query()` through the RO role; query/connection errors return as message text so the graph never crashes. All Anthropic calls go through the `app/llm.py` factories (the one place to later add retry/timeout/cost tracking): `get_client()` (sync, used by the offline extraction) and `get_async_client()` (used by the graph nodes). Importing the module no longer runs the graph — the demo `ainvoke` is behind `if __name__ == "__main__"` (`python -m app.agents.graph`). *Not yet:* a ReAct refinement loop in the worker, and `extraction`/`RAG` workers.

**The synthesizer is always the last node.** `synthesizer` turns the SQL worker's raw output (`SQL: … / Result: [(7,)]`) into one pt-BR sentence, so `/ask` returns prose instead of a tuple dump. Wiring: the supervisor's conditional edge now maps `END → "synthesizer"` and the synthesizer edges to `END` — **`route()` did not change**, it still returns `END`; only the `path_map`'s destination for that value did, which is why the routing logic stayed untouched. Three decisions carry weight. (1) **No worker result → static sentence, no LLM call**: on the unsupported-question path (and on a circuit breaker that cut before any query) there is nothing to synthesize, and paying a call to write "I don't know" is burning money; that's why `NO_ANSWER` now lives in `graph.py` rather than `app/main.py` — the graph writes the answer, the API only reads it. (2) **Free text, not structured output** — unlike every other node, the payload is one prose sentence, and forcing a tool would only wrap a string in JSON. This is also what the test fakes dispatch on: *no `tools` in the call ⇒ it's the synthesizer*. (3) **A failed synthesis degrades to the worker's raw text** (`frase or resultado`, covering both the exception and an empty response) instead of raising in the last node — ugly to read, but it is a real, already-paid answer, and 500-ing an `/ask` that already has the data is strictly worse. Cost is recorded through the same best-effort `_record_cost` with `agent_name="synthesizer"`. `tests/test_synth.py` pins all four behaviours; the load-bearing assertion is `synth_calls == 0` on the fallback path, which is what proves the "don't pay to say I don't know" rule.

**The graph nodes are async; the SQL access is not.** `supervisor`, `sql_worker` and `synthesizer` are `async def` so they don't block FastAPI's event loop on LLM calls. `get_schema()`/`run_query()` stay **psycopg3 sync** (one fresh connection per call, no pool) and are called through `asyncio.to_thread(...)` — deliberately: swapping the MCP server to an async driver would fork the one implementation the stdio server and the in-process worker share. `route()` stays sync — it only reads `State`, no I/O.

**`POST /ask` (`app/main.py`).** `{question: str (3..500)}` → `{answer, iterations}`, invoking `graph.ainvoke`. `_final_answer()` reads `state["messages"][-1]` and returns it when it's the `AIMessage` named `final` — since the synthesizer closes every exit path, the answer *is* the last message and there is nothing to scan for. The `NO_ANSWER` check on that message is only a belt: if the history ever ends with something else, we return the fallback rather than handing an agent's internal reasoning to the caller as an answer. `tests/test_ask.py` exercises the whole graph with a fake async client (dispatching on the forced tool name) plus fake `get_schema`/`run_query`, so **no test spends money**; the load-bearing case is the circuit breaker — a supervisor that never chooses `END` must stop at `MAX_ITERATIONS`.

**Auth + rate limit on `/ask` (`app/auth.py`, `app/limits.py`).** `/ask` is the only paid endpoint, so it's closed; `/health` and `/health/db` stay **open** (Railway's healthcheck sends no `Authorization`). `API_TOKENS` is `"nome:token,nome2:token2"` — tokens carry an **identity**, not one shared secret, which is what makes per-client limits and single-client revocation possible. `_load_tokens()` reads the env **inside the function** (importing `app.main` must not require env vars, and tokens can rotate without a rebuild). Fail-closed on config: missing/empty `API_TOKENS` → **500**, not 401 — a 401 would disguise a broken deploy as a bad client credential. Token comparison uses `secrets.compare_digest` over **all** tokens with **no `break`** (`==` leaks the correct prefix by timing; a `break` would leak the position in the list), and compares **bytes** — `compare_digest` on `str` raises `TypeError` on non-ASCII, and the credential comes from a client-controlled header, so a token with an accent would 500 instead of 401. The token is never logged, not even on failure. Two slowapi limits apply, **at different layers, and the split is load-bearing**. The per-IP ceiling (`ASK_RATE_LIMIT_IP`, default `10/minute`) is a `default_limits` enforced by `SlowAPIMiddleware`, which runs before routing and dependencies — so it also counts requests that die at the **401**. It covers every non-exempt route but is **counted per path** (slowapi's `key_style` defaults to `"url"`, so the bucket key is `(IP, path)`) — `10/minute` is per route, not across the API. As a route decorator it was never reached (`require_client` is a dependency, and FastAPI resolves dependencies before invoking the endpoint), which let anyone hammer `/ask` with invalid tokens for free. The per-client quota (`ASK_RATE_LIMIT_CLIENT`, default `30/hour`) stays a **route decorator** because it keys on `request.state.client_name`, which only exists after auth. The Limiter's global `key_func` is therefore `get_remote_address` (`default_limits` inherits it) and `client_key` is passed explicitly on the decorator. **No double counting** — verified in slowapi 0.1.10's `_check_request_limit`: the default limits are folded into the route check only when `combined_defaults` is true, i.e. when every route limit has `override_defaults=False`, and `.limit()` defaults it to `True`; so the middleware pass evaluates only the IP ceiling and the decorator pass only the client quota. **Landmine:** `_should_exempt` skips the middleware entirely for any route present in `_route_limits`, and only *static* limits land there (callables go to `_dynamic_route_limits`) — turning `ask_client_limit` into a plain string would silently stop the IP ceiling from covering `/ask`'s 401s; `test_teto_por_ip_cobre_request_sem_auth` is the guard. `/health` and `/health/db` are `@limiter.exempt` (inside `@app.get`, so the registered route is the marked function): Railway polls them in a loop, and quota burned there would return 429 to the platform, which then tears down a healthy service. Both limits are read from env through **callables**, so they're re-evaluated per request and the tests can tighten them; `_limit_from_env` validates with `limits.parse_many` and falls back to the default, because slowapi **fails open** on an unparseable limit (logs and applies none), so a typo in the Railway env would silently switch off the spend ceiling. `require_client` writes `request.state.client_name` **itself** — the decorator's wrapper builds its key at endpoint-call time, so an assignment in the route body would land too late. Deploying behind a proxy needs `uvicorn --proxy-headers --forwarded-allow-ips=<proxy>`, otherwise every request carries the proxy's IP and the per-IP ceiling treats all callers as one.

**Intended (not built):** the extraction and RAG workers, a ReAct loop in the SQL worker, and a HMAC-verified WhatsApp (Meta Cloud API) surface.

## SUSEP corpus pipeline (`scripts/`)

The harvester builds the corpus from three login-free public SUSEP endpoints. Critical gotchas baked into `susep_harvest.py`:
- The Olinda OData index (`DadosProdutos`) **only accepts `$format=json`** — any `$top`/`$filter`/`$select` returns HTTP 500, so the full dataset is fetched and cached locally.
- The version-resolution endpoint enforces a **~14-query-per-session quota**, after which it returns HTTP 200 with an *empty page* (not 429). The harvester detects this and rotates the session cookie to reset the quota, keeping ~1 req/s.

```bash
python scripts/susep_harvest.py                # in-force version per process
python scripts/susep_harvest.py --all-versions # full version history
python scripts/susep_harvest.py --limit 5      # smoke test
```

**Script defaults are anchored to the repo root** via `Path(__file__).resolve().parent.parent`, so they read/write `data/corpus/` correctly regardless of CWD (run them from anywhere; override with `--out`/`--index-cache`).

**The PDFs are gitignored** (`data/corpus/*.pdf`) — large and public. Only `corpus_manifest.json` is committed; it records per-version provenance (process, internal id, insurer, CNPJ, url, sha256, dates, `has_text`) and lets anyone re-download and verify the corpus by hash. The download endpoint keys on an **internal numeric id**, while the index keys on **process number** (`15414.NNNNNN/AAAA-DD`) — bridging the two is what the resolve step does.

The extraction logic lives in **`app/extraction/`** (importable modules: `pdf` → `extract` → `schema` → `persist`, plus `manifest`, `batch`, `sample`, `evaluate`); the `scripts/` files are thin CLI wrappers over it. The split is deliberate — persistence can be re-run without paying for the LLM again:
- `scripts/run_extraction.py <pdf> --out <json>` — pdfplumber → Anthropic forced tool-use (single tool, `input_schema` = the Pydantic tree, `tool_choice` forced) → validated **nested** output, cross-checked against the manifest. Needs `ANTHROPIC_API_KEY`.
- `scripts/persist_extraction.py <json> --pdf <pdf>` — deterministic flatten of the nested tree into the 5 tables; the LLM returns a tree because it doesn't know DB ids, and this layer assigns ids/FKs. Provenance comes from the manifest, not the LLM read. Needs `DATABASE_URL`.
- `scripts/run_batch.py` / `app/extraction/batch.py` — mass extraction via the **Batch API at 50% price** (offline, nobody waiting); `sample.py` picks the corpus sample; `evaluate.py` scores a cheaper model against a hand-checked golden (`data/golden/`). `rescue_batch.py` re-reads an already-paid batch's results (they persist ~29 days) so a local *parse* failure costs nothing to retry.

The extracted JSON under `data/extractions/` is gitignored derived output, like the PDFs.

The other scripts are one-off, not production: `susep_probe.py` (blind-sampling viability probe that established corpus volume) and `pilot_extraction.py` (manual hand-read extraction of 2 CGs that validated the schema — produces `data/pilot_extraction.json`, summarized in `data/pilot_findings.md`).
